# 录制即执行（Record & Run）技术方案

## 1. 目标

录制完成后一键执行，不经过候选评分→人工提升→生成用例的中间环节。
录制产物和已治理页面元素互不污染。

## 2. 数据模型

### 2.1 现有表（不变）

| 表 | 所属世界 | 用途 |
|----|---------|------|
| `page_object_recorder_sessions` | 录制 | 录制会话 |
| `page_object_candidate_elements` | 录制 | 候选元素（未提升） |
| `page_object_candidate_groups` | 录制 | 候选分组 |
| `page_objects` | 治理 | 正式页面对象 |
| `page_elements` | 治理 | 正式元素（已审核） |
| `test_cases` | 治理 | 正式用例 |
| `test_case_executions` | 治理 | 执行记录 |

### 2.2 新增表

**不需要新表。** 录制执行复用 `test_cases` + `test_case_executions`。
录制的临时用例通过 `source = "recorder"` 和 `tags` 中的 `session:<id>` 标记区分。

### 2.3 隔离保证

```
page_object_recorder_sessions ──生成──→ test_cases (source="recorder", temporary)
                                               │
                                               ▼ run_case()
                                        test_case_executions
                                               │
                                     ┌─────────┴──────────┐
                                     │ 用户满意？           │
                                     ├────────────────────┤
                                     │ YES: promote候选→正式 │
                                     │      case.status→active │
                                     │ NO:  删除case+候选    │
                                     └────────────────────┘
```

**promote 是单向门。** 候选→正式元素的提升仍需人工触发，不可逆。

## 3. API 设计

### 3.1 新增端点

```
POST /api/page-objects/recorder/sessions/{session_id}/run
  ↓
1. 校验 session 已停止
2. 调用 create_test_case_draft_from_session() 生成临时用例
3. 调用 facade.run_case() 执行
4. 轮询 get_run() 等待执行完成
5. 返回 { case_id, run_id, status, report_url, candidate_summary }
```

### 3.2 修改端点

`POST /api/page-objects/recorder/sessions/{session_id}/stop` 增加可选参数：
```json
{
  "verify_locators": true,
  "run_immediately": false   // 新增
}
```

`run_immediately=true` 时，stop 完成后自动触发 run。

### 3.3 查询端点

```
GET /api/page-objects/recorder/sessions/{session_id}/runs
  ↓ 返回该 session 的所有执行历史
```

## 4. 执行流程

```text
stop_recorder_session(run_immediately=True)
  │
  ├─ 1. _stop_codegen_process()
  ├─ 2. _parse_codegen_steps()  → 录制步骤
  ├─ 3. create_test_case_draft_from_session()
  │      ├─ _build_case_steps_from_recorded_steps() → DSL steps
  │      ├─ _build_case_script_from_recorded_steps() → script_code
  │      └─ test_case_service.create_test_case() → TestCase (source="recorder")
  │
  ├─ 4. facade.run_case(case_id=...)
  │      └─ workbench_runtime_service.execute_run()
  │           ├─ pytest + Playwright
  │           └─ Allure 报告
  │
  └─ 5. 返回 { session, case_id, run_id, status }
```

## 5. 定位器策略

录制执行用的定位器优先级：

| 优先级 | 来源 | 示例 |
|--------|------|------|
| 1 | 已有 PageElement（recorded element_code 匹配） | `element:login-username-input` |
| 2 | 候选元素最佳 locator（S/A tier） | `data-testid:username` |
| 3 | 原始录制 locator | `css:.login-form input[type=text]` |

策略 1 已通过 `promote_candidate_group` 实现（提升后写入 `page_elements`）。
策略 2/3 需要 `_build_case_steps_from_recorded_steps` 中增加回退逻辑——如果录制步骤中某元素的 `element_code` 不在 `page_elements` 表中，使用候选的最佳 locator。

## 6. 污染防护

| 场景 | 防护 |
|------|------|
| 录制执行失败 | 临时用例标记 `status=temporary`，不影响正式用例列表 |
| 定位器写入了错误数据 | 候选元素写入 `candidate_elements` 表，不写 `page_elements` |
| 用户误点 promote | `promote_candidate_group` 校验候选状态 + 写 governance log |
| 录制用例混入正式用例列表 | `list_cases` 按 `source != "recorder"` 过滤（列表页不显示） |
| 录制用例混入质量门 | `workbench_quality_gate_summary` 按 `source != "recorder"` 过滤 |
