# 项目问题总结与防范方案

> 从"第 3 次重构"的角度回顾所有问题、根因、解决方案和未来防范措施。

---

## 一、架构层面

### 1.1 没有 Repository 层 → raw SQL 散落 200+ 处

**问题：** Service/Facade/Router 中随处写 `db.execute(select(Model).where(...))`，换数据库、加缓存、改查询逻辑都需要全局搜索替换。

**根因：** 项目初期没有规划数据访问层。模型定义后直接在各处写 SQL。

**解决：** 创建 6 个 Repository 聚合根（TestCase、PageObject、Recorder、TestProject、TestDataPool、WorkbenchState），封装 ~140 处 `db.execute(select(...))`。CI 护栏拦截新增违规。

**防范：**
- **铁律 1：所有 DB 查询必须通过 Repository。** 唯一允许写 `db.execute(select(Model)...)` 的地方是 `app/repositories/` 目录。
- CI 脚本 `check_architecture.py` 自动扫描拦截。

### 1.2 SessionLocal 散落 7 处 → 事务边界模糊

**问题：** 7 个文件中出现 `with SessionLocal() as db:`，绕过 FastAPI 的 `Depends(get_db)`。同一请求可能在多个事务中执行。

**根因：** 部分函数（子进程执行、后台线程）确实需要独立 Session，但大部分只是"拿到一个 db 对象就行"的惯性写法。

**解决：** `workbench_state_store.py` 8 个函数增加可选 `db` 参数。facade 5 处 `store.append_history()` → `store.append_history({...}, db=db)`。剩余 2 处（后台线程/生成管线）确需独立 Session，已文档化。

**防范：**
- **铁律 2：Service/Repository 绝不自己 `SessionLocal()`。** 通过参数接收 `db: Session`。
- CI 自动扫描拦截（排除数据库层和已文档化的例外）。

### 1.3 两套技术栈 → Flask + FastAPI 混用

**问题：** orchestrator 用 Flask（手动参数解析、`jsonify` 序列化、WSGI→ASGI 适配器），web-ui 用 FastAPI。同一个数据库两种连接方式（`sqlite3.connect` vs SQLAlchemy）。

**根因：** orchestrator 是早期独立开发的 AI 编排服务，选择了 Flask。后期 web-ui 选择了 FastAPI。

**解决：** orchestrator Flask→FastAPI 迁移（`app.py`→`main.py`），`sqlite3.connect()`→`shared_backend.db.get_db_session()`。两个服务统一为 FastAPI + uvicorn。

**防范：**
- 新服务必须使用 FastAPI。
- `import sqlite3` 列入 CI 禁止项。

### 1.4 同一个数据 5 个事实源 → 改东西不确定"系统信哪个"

**问题：** `DB.script_code`、`assets/test-cases/*.yaml`、`web-ui/state/generated-cases/`、`web-ui/state/test-points/`、`test_case_executions` 同时存储同一份用例数据。YAML 回退逻辑让旧 YAML 覆盖 DB 的 `script_code`。

**根因：** 系统演进过程中各层独立增加了缓存/快照/回退机制，没有明确"哪个是权威"。

**解决：**
- `script_code` 确定为唯一可执行事实源。YAML 回退逻辑已删除（空 `script_code` → 422）。
- README 5.2 事实源 4 层层次图：唯一真理 → 派生资产 → 可重建缓存 → 运行时记录。
- `web-ui/state/README.md` 明确标记可重建目录。

**防范：**
- **铁律 3：执行只用 `script_code`。** YAML 是展示视图，不直接执行。
- 新增缓存/快照必须明确标记"可重建"。

## 二、代码质量

### 2.1 死代码 2,000+ 行 → `git add -A` 误引入 300+ 文件

**问题：** `legacy/`、`auto_run_*`、旧测试文件、`code_explanations/`、`allure-report/`、Docker 缓存等文件长期残留或被误提交。

**根因：** 
- 日常开发中功能下线但文件未删除。
- **一次 `git add -A` 把所有磁盘上的历史遗留文件全部提交进 Git。**

**解决：**
- 删除 1,985 行死代码 + 115 个过期文件 + 61 个旧前端文件 + 14 个旧模板。
- 从 Git 历史中删除 `allure-report/`、`backups/`、`.docker-buildx/`。
- 更新 `.gitignore` 防止同类问题。

**防范：**
- **铁律 4：永远不要 `git add -A`。** 只用 `git add <具体文件>` 或 `git add -u`。
- CLAUDE.md 置顶红色警告。

### 2.2 重复函数 22+ 处 → `_dict_value` 定义 10 次

**问题：** `_dict_value` 在 10 个文件中独立定义，`_list_value` 8 次，`_normalized_text` 3 次。相同逻辑到处复制。

**根因：** 没有共享工具层。开发者（包括 AI）遇到"需要一个 dict 安全访问器"就直接在本地写，没意识到别处已有。

**解决：** 创建 `shared_backend/type_utils.py`（14 个公共函数）。22 处重复定义全部替换为 import。CI 自动检测新增重复。

**防范：**
- **铁律 5：写工具函数前先查 `shared_backend/type_utils.py`。** 如果有 → import。如果通用 → 加到 type_utils。
- CLAUDE.md 的 AI 代码模板包含决策树。

### 2.3 573 行单函数 → `run_generate_pipeline` 不可读

**问题：** 生成管线入口函数 573 行，无子函数拆分，新同事需要一次性理解全部逻辑才能改任何一步。

**根因：** 管线逻辑不断累加（DSL 校验、候选处理、错误分类、日志脱敏），从未被拆分。

**解决：** 拆为 6 个步骤函数（88/75/120/103/45/142 行）+ 主函数 113 行管道。每步可独立理解、独立测试。

**防范：**
- **铁律 6：单个函数 ≤ 200 行，≥ 100 行警告。** CI 自动检查。
- 拆分时使用上下文对象（dataclass/dict）在步骤间传递状态。

### 2.4 `except Exception` 129 处 → 吞掉真实错误

**问题：** `json.loads` 捕获 `except Exception` 而非 `json.JSONDecodeError`。真实 bug 被静默吞掉。

**根因：** 开发者不确定具体异常类型，用了最宽泛的捕获。

**解决：** 34 处替换为具体类型（`json.JSONDecodeError`、`yaml.YAMLError`、`OSError`）。剩余 95 处为编排降级/DB 回滚/re-raise 场景，已确认合理。

**防范：**
- **铁律 7：只用具体异常类型。** `except Exception` 仅在编排降级、DB 回滚、子进程容错时允许。
- pre-commit 检测裸 `except:`（ruff B904 规则）。

## 三、测试

### 3.1 测试覆盖不足 → 125 个测试

**问题：** 重构前仅 ~125 个测试，facade.py 0 测试、orchestrator 仅 2 个单元测试、多个 service 零覆盖。

**根因：** 项目早期以功能开发为主，测试后补。

**解决：** 增加到 276 个（+151）。覆盖 facade 全方法、Repository 方法、governance_service、reporting/task 纯函数、orchestrator core、pipeline 步骤函数。

**防范：**
- CI 结合作者新增覆盖率检查（TODO：低于阈值 CI 警告）。

### 3.2 15 个 test ordering 失败 → monkeypatch 状态污染

**问题：** 276 个测试独立运行全绿，一起运行 15 个失败。每次 `pytest -q` 不可信任。

**根因：** 多个测试文件的 `monkeypatch.setattr` 修改相同模块属性，撤销顺序在 full suite 中错乱。不是单一测试导致，是累积效应。

**解决：** 
- Workaround：`make test-unit` 分两批运行（44 + 232 = 276 passed）。
- 根因修复：需将 44 个测试的 monkeypatch 改为 `unittest.mock.patch` 上下文管理器（TODO）。

**防范：**
- 新增测试推荐使用 `unittest.mock.patch` 而非 `monkeypatch.setattr`。
- 已有 monkeypatch 测试逐步迁移（列为技术债）。

## 四、文档

### 4.1 README 只有架构图，没有业务链路

**问题：** 原来的 README 有 Mermaid 架构图但没有"从需求到 YAML 到底怎么走的"。新同事需要读代码才能理解业务。

**解决：** README 新增 8 个业务链路章节（生成/执行/治理/录制/DSL/Agent/数据模型/分层架构）。CLAUDE.md 新增 AI 开发规则。

### 4.2 onboarding 文档引用不存在的文件

**问题：** `docs/onboarding/README.md` 引用 6 个 `.md` 文件，全部不存在。

**解决：** 重写为实际可用的指引（README → CLAUDE.md → Makefile → state/README）。

### 4.3 50 个过期文档未清理

**问题：** `docs/implementation-plan/`、`docs/history/`、`docs/product/`、`docs/rule/` 共 50 个文件全部是 2026 年 3-4 月的旧计划，已执行或废弃。

**解决：** 全部删除。保留当前有效的 architecture/core/bugfixes/acceptance。

## 五、基础设施

### 5.1 CI 不跑单元测试

**问题：** `tests.yml` 只跑 static-baseline（ruff + mypy + contract），不跑 276 个 unit tests。

**解决：** 新增 `unit-tests` job，PR 时自动运行 `make test-unit`。

### 5.2 没有架构护栏

**问题：** 文件膨胀、Repository 绕过、Session 泄漏、函数重复——这些问题只能在代码 review 中发现。

**解决：** `scripts/ci/check_architecture.py`（6 项检查 + baseline 机制）。CI 自动运行，只拦截新增违规。

### 5.3 本地开发没有一键启动

**问题：** 新人需要分别启动 Docker、跑 seed、build 前端。

**解决：** `make dev`（一键：Docker up → seed → 前端 build → 服务就绪）。

### 5.4 `app.py` 和 `app/` 包冲突

**问题：** orchestrator 的 `app.py` 和 web-ui 的 `app/` 包在同一 PYTHONPATH 中冲突。

**解决：** orchestrator: `app.py` → `main.py`。
