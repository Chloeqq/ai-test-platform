## 2. Dashboard 指标可行性分析

### 指标 A：项目质量评分 ✅ 支持

计算方式：`avg(quality_report.score)` + `count_by_decision` + `worst_assets`
限制：需逐 asset GET（无批量 quality 查询 API）

### 指标 B：资产质量排名 ✅ 支持

排序 by score。限制：无批量查询，需遍历所有 asset 文件。

### 指标 C：问题分布 ✅ 支持

数据源：`get_quality_gate_violations(asset)` → violation list。所有字段已有。

### 指标 D：AI 生成质量分析 ⚠️ 部分支持

| 子问题 | 支持 | 说明 |
|--------|------|------|
| AI 最近生成质量有没有提升？ | ❌ | 无历史 quality 快照 |
| 哪个 Agent 生成最差？ | ⚠️ | source_type 区分 AI/manual，无 Agent 级标识 |
| 哪类需求容易失败？ | ❌ | 需求文本未持久化关联到 quality 结果 |

### 指标 E：趋势分析 ❌ 不支持

- `quality_report` 不持久化 → 无法回溯历史
- 无 `quality_history` 表/文件
- asset `version` 递增但旧版本被覆盖
- 唯一可用时间序列：`asset.updated_at` + `case.created_at` + execution runs

## 3. 数据缺口汇总

| 指标 | 当前支持 | 缺少字段 | 最小补充 |
|------|---------|---------|---------|
| 项目评分 | ✅ | 批量查询 API | 无需新增数据 |
| 资产排名 | ✅ | 批量查询 API | 无需新增数据 |
| 问题分布 | ✅ | — | 无需新增数据 |
| Agent 分析 | ⚠️ | source 级 Agent 标识、需求-质量关联 | 小 |
| 趋势分析 | ❌ | quality_history 快照 | **关键缺口** |

## 4. 数据一致性风险

### 风险 1：quality_report 实时计算 → 历史不可靠

quality_report 在每次 GET 时重新计算。如果 asset 被编辑过，历史质量数据无法还原。趋势分析必须存储快照。

### 风险 2：asset 修改后质量变化无法溯源

version 递增，旧值丢失。无法回答"提升来自哪个改动"。快照需包含 previous_score 和 delta。

### 风险 3：review_history 不足

point.metadata.review_history 当前为空。无法分析审核效率（平均审核时间、reject 率、重复审核次数）。

### Phase 5.1：Quality Snapshot

目标：使趋势分析成为可能。

方案：在 asset 保存/更新时（upsert_test_point_asset），追加 JSONL 快照。

```
web-ui/state/quality-snapshots/{project}/{asset_id}.jsonl

{"version":1,"at":"...","score":60,"decision":"REJECT","zero_assertion":4,...}
{"version":2,"at":"...","score":90,"decision":"REJECT","zero_assertion":1,...}
```

修改：
- `facade_test_point_assets.py:upsert_test_point_asset` — 保存后追加 snapshot
- 新增 `append_quality_snapshot()` + `get_quality_timeline()` (~35行)

必要性：不实施 = 无法做任何历史趋势对比。
