## 一、Context(为什么做)

参考项目 BrickCore 的核心亮点是「上传 PRD → AI 批量生成功能用例」,其中 **docx/pdf 文档结构化解析** 是本平台当前最大的缺口:

- 本平台 `agents/requirement-parser-agent/src/tools/document_fetcher.py` 只能抓 HTTP 文本(JSON/YAML/纯文本),把 bytes 强行 `decode(utf-8)`,**无法处理 docx/pdf 二进制**。
- 前端 `AiGenerationPage.tsx` 只有一个 textarea,**完全没有文件上传能力**,也没有 MinIO/对象存储。
- 用户只能手动把需求粘成纯文本,无法直接传 Word/PDF 的 PRD。

**目标**:用户上传 docx/pdf/md 需求文档 → 原始文件存 MinIO 存档(供审计/重解析)→ 解析成**结构化 Markdown**(保留标题层级和表格)→ 填入现有 `requirement` 字段 → 走现有 LLM 需求解析链路生成测试点。

**链路复用点(已确认,零改动)**:解析出的 markdown 文本填入前端 textarea 的 `requirement` 字段,最终喂给现有 `POST /api/workbench/preview-test-points` → orchestrator `/requirements/parse` → 子进程 `agent.py`(`requirement` 非空时作为 LLM source,见 `agent.py:308-317`;`prd_text` 分支在 `agent.py:318-326`,本方案不走该分支)。**「上传+解析」全部发生在 web-ui-service 端,orchestrator 和 agent 子进程零改动。**

## 二、架构约束(CLAUDE.md 护栏)

- DB 访问只走 Repository(`db.execute(select(...))` 仅 Repository 层)
- Service/Facade 不 `SessionLocal()`,透传 `db: Session`
- 异常捕具体类型(`zipfile.BadZipFile` / `json.JSONDecodeError` / `ValueError` / PyMuPDF `fitz.FileDataError`),不新增裸 `except Exception`
- 行数红线:router≤200 / service≤1000 / repository≤400 / 单函数≤370
- 工具函数先查 `shared_backend/type_utils.py`

## 三、关键取舍

- **解析模块放 `web-ui-service/app/services` 而非 `shared_backend`**:PyMuPDF 是 C 扩展,不应污染被两个服务共享的 shared_backend(避免 orchestrator 也被迫装 PyMuPDF)。
- **docx 用 stdlib zipfile 解析(零依赖)**,参考 BrickCore `document_structure.py:_load_docx_structured`(解 `word/document.xml`,沿 `word/styles.xml` 的 `basedOn` 解析标题层级,按阅读顺序抽 heading/paragraph/table)。BrickCore 是 Tortoise,只搬纯解析逻辑,不搬 DB 部分。
- **pdf 用 PyMuPDF(fitz)**:BrickCore 同方案,逐页 `get_text()`。纯 Python 替代 pdfplumber 质量低。
- **MinIO 客户端仿 `redis_client.py`**:`lru_cache` + `enabled` 开关 + 优雅降级(`try import` 失败/未启用返回 None),不是类实例。
- **DocumentRecord 落库(本次纳入)**:既然存档就要能追溯(哪个文档、谁传的、object key、解析状态),因此新建 `requirement_documents` 表 + Repository + migration 一并做。
- **上传与提取测试点解耦**:上传端点只做「存 MinIO + 解析 + 落库 + 返回 markdown」,不串联 LLM。前端拿到 markdown 填进 textarea,用户可编辑后再点「提取测试点」走现有流程,避免上传接口长阻塞。

## 四、顺带修复的 Bug

`agents/requirement-parser-agent/src/agent.py` 存在真实 bug——调用签名不匹配,被宽 except 静默吞掉,导致 `prd_url` 和 `git_diff_path` **一直失效**:

- `agent.py:246` `fetch_document(url)` → 应为 `fetch_document(url=url)`(`document_fetcher.py:32` 是 keyword-only `def fetch_document(*, url, ...)`)
- `agent.py:254` `read_local_file(path, base_dir=str(self.repo_root))` → 应为 `read_local_file(path=path, repo_root=self.repo_root)`(`local_file_reader.py:11` 是 `def read_local_file(*, path, repo_root)`,形参名是 `repo_root` 不是 `base_dir`)
- `_safe_read_local_file` 返回处也要适配:`read_local_file` 返回 dict `{"path","text"}`,当前 `agent.py:104-107` 按 str 用,需取 `.get("text","")`

## 七、风险与应对

| 风险 | 应对 |
|------|------|
| docx 非常规结构(文本框/SmartArt/分节符) | `_parse_docx_to_blocks` 每段 try 具体异常,失败段跳过不阻断;解析异常仍返回已成功部分并标 `parse_status=partial` + `parse_error`,markdown 可编辑 |
| docx 标题层级识别失败 | 优先 `outlineLvl`、fallback 样式继承链(见 Phase 2) |
| pdf 多栏阅读顺序错乱 | PRD 多单栏风险低;`_blocks_to_markdown` 注释标明;未来用 `get_text("dict")` 按 y 排序 |
| 大文件撑内存 / nginx 413 | app 层 20MB 上限 + nginx `client_max_body_size 20m`(见 Phase 1/3) |
| MinIO 未启用 | `minio_enabled=false` → client 返回 None → service 报 503,不静默 |
| MinIO 启用但连不上 | `upload_bytes` 捕 `(S3Error, MaxRetryError)` 返回 False → service 报 503(不裸 except) |
| MinIO 孤儿对象 | 落库顺序:先 `create(pending)` 记 object_key,再解析更新状态 |
| 存储清理非原子 | `is_deleted` 软删除 + MinIO bucket 生命周期规则(如 180 天过期) |
| PyMuPDF AGPL | 内部服务不分发,无合规问题;团队有顾虑可换 pdfplumber(MIT,质量略低) |
