## 与当前仓库对齐的优先级修正版

上面的路线图适合作为目标态，但如果按当前仓库现实推进，建议把顺序再压实一点：

| 顺序 | 优先级 | 建议项 | 理由 |
|------|--------|--------|------|
| 1 | P0 | 失败来源分类收口 | 这是当前最影响回归可信度的卡点 |
| 2 | P0 | 测试点中间层与追溯链路 | 需求到用例跳跃过大，必须先有可追溯资产层 |
| 3 | P0 | 页面分析规则优先化与置信度下沉 | 页面语义误判会放大后续所有 AI 输出误差 |
| 4 | P1 | `data-generation-agent` 企业级治理收口 | 最小可用已完成，下一步是模板 / registry / cleanup 增强 |
| 5 | P1 | 执行调度统一任务模型 | 没有任务模型就很难做稳定并发、重试和门禁 |
| 6 | P1 | 证据模型与生命周期治理 | 回归测试依赖证据闭环，产物必须先可管理 |
| 7 | P2 | Script Generation / Self-Healing 优化 | 这是增强层，不应早于基础闭环 |

### 实施时的三个边界

- 不建议把 9 个 Agent 同时拉到 L4，再反向找业务场景。
- 不建议先做“大而全的 AI 编排”，再补确定性校验器。
- 不建议把回归测试环节的 pass/fail 裁决交给 AI。

更稳妥的路径是：

1. 先让确定性底座稳定。
2. 再让 AI 负责语义补充和建议。
3. 最后才谈更复杂的自愈和风险预测。

### 当前建议先做的四件事

结合当前仓库现实，下一轮最值得优先推进的是：

1. 把失败来源分类先收口，保证回归结论可信。
2. 把测试点依赖追踪、低置信度继承和执行门禁继续收口。
3. 把页面分析进一步从“规则模块化”推进到“独立编排能力”。
4. 再推进 `data-generation-agent` 的企业级治理与 self-healing 边界治理。

这四件事比继续扩张外围 UI、更复杂的 AI 编排或伪实时成熟度百分比更有价值。
