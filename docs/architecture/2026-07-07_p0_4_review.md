# P0-4 反方审查：quality_report 架构评估

> **日期:** 2026-07-07
> **审查对象:** `asset_views.py:_build_quality_report()` (commit `ccb6406`)

---

## 1. 当前设计是否合理

### 问题 1: Quality Report 来源

**回答: B — asset_views.py 根据字段重新计算。**

`_build_quality_report` 的 decision 来源:
```python
if zero_assert_count > 0:    decision = "REJECT"
elif assertion_warnings:     decision = "REVIEW"
elif requires_review:        decision = "REVIEW"
else:                        decision = "PASS"
```

`quality_gate.gate.evaluate()` 的 decision 来源:
- 17 条规则 + ScoreEngine (5 维度: data/assertion/semantic/dependency/page_object)
- 需要编译后的 DSL (case_yaml), page_object, seed_data

**两者是不同的评分系统，不同输入，可能产生不同 decision。**

### Gate decision vs API decision 分歧场景

| 场景 | quality_gate decision | quality_report decision | 分歧? |
|------|----------------------|------------------------|------|
| 3 个零断言 functional 点 | RULE_008 FATAL → REJECT | REJECT (zero_assert_count=3) | ✅ 一致 |
| 全部有断言但 data 缺失 | RULE_002 ERROR → REVIEW | PASS | ❌ 分歧! |
| element_code 不匹配 | RULE_006 ERROR → REVIEW | PASS | ❌ 分歧! |

**根因:** `quality_gate` 在编译后运行 (有 case_yaml)，`quality_report` 在保存后运行 (只有 asset metadata)。两者的输入集不同。

## 2. 是否存在职责泄漏

### 当前分层

```
quality_gate/          ← Domain Service: 质量评分引擎 (17 rules, ScoreEngine)
  gate.py              ← CaseQualityGate.evaluate()
  scoring.py           ← ScoreEngine.calculate()
  rules/rule_*.py      ← 17 条具体规则

asset_views.py:        ← View Layer: API 响应构建
  _build_quality_report()  ← ⚠️ 包含质量评分逻辑 (score/decision)
```

### 职责泄漏

`_build_quality_report` 中的评分逻辑应该属于 `quality_gate` domain service，不应该在 view 层重新实现一套简化版。

**但是** — 当前 `quality_gate` 需要编译后的 `case_yaml` 作为输入，而测试点资产的 review 发生在编译前。所以 view 层无法直接调用 `quality_gate`。

**这是架构时序问题，不是代码放置问题。**

---

## 3. 数据一致性检查

### 场景 1: 资产生成后 Gate 结果变化

```
时刻 T1: save → _build_quality_report(data=T1) → decision=REVIEW
时刻 T2: regenerate → 断言修复 → _build_quality_report(data=T2) → decision=PASS
```

✅ `quality_report` 始终基于当前 asset 数据计算，每次请求都重新算，保持最新。

### 场景 2: 新增质量规则

新增 RULE_018 需要同步修改两处:
1. `quality_gate/rules/rule_018.py` (domain)
2. `_build_quality_report` (view) — ⚠️ 不一定需要改，除非规则影响 assertion 计数

**风险:** 如果新规则改变了 "什么是质量问题" 的判断标准，view 层的简单逻辑可能无法感知。但 MVP 的 `_build_quality_report` 只关注断言数量，这是一个稳定的基础指标。

### 场景 3: 多接口复用

当前 `quality_report` 只在 `build_test_point_asset_detail` 中。如果列表页也需要，需要复制或提取。

**建议:** 提取到 `quality_gate` 包作为 `build_asset_quality_report(asset)` 函数，多个 view 共用。

## 5. 调整建议

### 最小调整方案 (不改代码，仅记录)

**短期 (当前 MVP): 接受现状。**

| 理由 | 说明 |
|------|------|
| quality_gate 需要编译后 DSL | 测试点资产阶段没有 case_yaml, 无法调用 quality_gate |
| 评分逻辑简单透明 | 仅基于断言计数, 不是复杂规则引擎 |
| 两套系统覆盖不同阶段 | quality_gate=编译后质量, quality_report=保存后审计 |
| 分歧概率低 | 断言数量是最重要的质量信号, 与 RULE_008 一致 |

**中期 (P1): 提取到 domain 层。**

```python
# quality_gate/asset_quality.py (新文件)
def build_asset_quality_report(asset: dict) -> dict:
    """从 asset metadata 计算质量报告。
    
    轻量版本, 不依赖编译后的 case_yaml。
    与 CaseQualityGate 互补: Gate 在编译后, Report 在保存后。
    """
```

**长期 (P2): 统一 Gate 输入。**

让 `CaseQualityGate` 支持 `GateContext(case_yaml=None)` 模式，对未编译的资产跳过需要 case_yaml 的规则，只运行数据层面的规则。

## 6. 结论

```
═══════════════════════════════════════════
当前设计: 可接受 (MVP), 有技术债务但可控
═══════════════════════════════════════════
```

| 维度 | 评估 |
|------|------|
| 数据源一致性 | ⚠️ quality_gate≠quality_report, 但覆盖不同阶段, 当前不冲突 |
| 职责泄漏 | ⚠️ 评分逻辑在 view 层, 但 quality_gate 无法在编译前运行, 无奈之举 |

| 可复用性 | ⚠️ 函数在 view 层, 列表接口复用需提取 |

**不需要立即调整。** 当前实现满足 MVP 需求 (审核页展示质量报告)，架构问题有明确升级路径。
