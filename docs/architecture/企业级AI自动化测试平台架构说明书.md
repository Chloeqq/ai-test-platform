## 一、架构总览（完整版）

本平台采用分层架构设计，遵循 “高内聚、低耦合” 原则，从输入源到发布决策形成完整闭环，核心补齐「测试资产中心 - 页面对象模块」，补充企业级权限、审计、评审能力，明确各层依赖关系，确保每一层职责清晰、可独立扩展，同时解决当前页面对象空白导致的架构空转问题。

## 二、各层详细设计（重点完善页面对象模块）

### 2.1 输入源层（基础层，已有基础，补充细节）

#### 2.1.1 核心功能

作为平台的 “原料输入口”，采集各类与测试相关的原始数据，为后续测试资产生成、AI 解析提供基础，确保输入源全面、准确、实时。

#### 2.1.2 各输入源详细说明

- **PRD（产品需求文档）**：支持上传 Word、Markdown、飞书文档等格式，提取产品功能需求、业务规则、页面描述、交互逻辑，作为 AI 生成用例的核心依据。

- **Swagger/OpenAPI**：自动对接接口文档，提取接口路径、请求方法、参数、响应格式，生成 API 契约，关联 API 自动化用例，无需人工手动录入接口信息。

- **Git Diff**：对接代码仓库（GitLab/GitHub），捕获代码变更记录，识别新增 / 修改 / 删除的功能、接口、页面，触发针对性测试（如增量回归）。

- **缺陷单**：对接缺陷管理工具（Jira / 禅道），提取缺陷描述、复现步骤、涉及模块 / 页面，自动生成回归用例，确保缺陷修复后可快速验证。

- **线上日志**：采集线上应用日志（如 ELK 日志），识别线上异常、高频报错，反向生成测试用例，弥补线下测试盲区，提升平台测试覆盖率。

#### 2.1.3 输出内容

标准化原始数据（结构化格式），供测试资产中心、AI 编排层调用，例如：PRD 解析后的业务规则、Swagger 解析后的 API 契约、Git Diff 的代码变更详情等。

### 2.2 测试资产中心（核心层，重点补齐页面对象模块，解决当前空白）

平台的 “核心资产底座”，所有测试相关的可复用资产均在此集中管理，是连接输入源层、AI 编排层、自动化执行层的关键桥梁，当前重点补齐页面对象模块，解决 “无元素可操作、用例无法执行” 的核心问题，同时补充企业级的权限、审计能力。

#### 2.2.1 核心模块（重点完善页面对象库）

##### [2.2.1.1](2.2.1.1) 页面对象库（Page Object Library，当前空白，重点落地）

核心目标：提供 100% 准确、可复用、可维护的页面对象（页面 + 元素），作为 Web/Mobile 自动化执行的核心依赖，杜绝 AI 生成用例与实际页面脱节的问题。

###### 1. 核心组成

- **页面管理**：管理所有测试相关页面，建立页面与模块的关联，支持页面的增删改查、批量操作。

- **元素管理**：管理页面下的所有元素，存储元素的定位器、属性、归属页面，支持元素的录制、编辑、删除、健康检查。

- **录制器（核心工具）**：基于 Playwright 实现，支持用户手动录制页面元素，自动捕获元素定位器（优先 id、data-testid、css，兜底 xpath），确保元素定位 100% 准确。

- **页面对象模板**：提供标准化页面对象模板，支持自动生成页面对象代码（Python/Java），供自动化执行层、脚本生成 Agent 调用。

- **健康检查**：定时巡检页面元素的有效性，若元素失效（如定位器变更），自动告警并标记状态，确保页面对象始终可用。

###### 2. 数据存储设计（MySQL 表结构，企业级规范）

**页面表（page）**

|page_code|varchar(64)|页面唯一编码（如 LoginPage）|

|page_url|varchar(256)|页面访问 URL|
|module_id|bigint|所属模块 ID|

|create_time|datetime|创建时间|
|update_time|datetime|更新时间|
**元素表（element）**

|字段名|类型|说明|
|---|---|---|
|element_id|bigint|元素唯一 ID|
|element_code|varchar(64)|元素唯一编码（如 username_input）|
|element_name|varchar(128)|元素中文名称|
|page_id|bigint|所属页面 ID|
|locator_type|varchar(32)|定位器类型（id/css/xpath 等）|

###### 3. 核心功能细节（可直接落地）

- **录制器功能**：用户输入页面 URL，点击 “开始录制”，平台自动打开 Playwright 浏览器，用户点击页面元素后，自动捕获元素的定位器（优先选择最稳定的定位方式，如 id>data-testid>css>xpath），用户输入元素中文名称后，自动保存到元素表，同时更新页面表的 element_count 字段。

- **元素健康检查**：后台定时任务（每天凌晨执行），遍历所有页面，通过 Playwright 打开页面，验证每个元素的定位器是否有效，若无效，将 health_status 设为 0，并发送告警（通知测试 / 前端人员）。

- **页面对象复用**：支持跨用例、跨项目复用页面对象，同一页面的元素只需录制一次，所有关联用例均可调用，减少重复工作。

- **版本管理**：支持页面对象、元素的版本回溯，若元素定位器变更，可回滚到历史版本，避免误操作导致的用例执行失败。

##### [2.2.1.2](2.2.1.2) 用例库（Case Library）

核心目标：存储 AI 生成、人工维护的所有测试用例，关联页面对象、API 契约、数据模板，确保用例可执行、可复用、可追溯。

- 用例类型：Web 自动化用例、API 自动化用例、Mobile 自动化用例、手动用例。

- 用例结构：用例 ID、用例标题、优先级、所属模块、关联页面 / API、前置条件、测试步骤（关联页面对象元素 / API 契约）、预期结果、数据模板、标签、状态（待评审 / 未执行 / 通过 / 失败 / 阻塞）。

- 核心关联：Web 用例步骤关联页面对象的元素（只存储 element_code，不存储定位器，确保元素变更后用例无需修改）；API 用例关联 API 契约（关联接口路径、参数模板）。

- 新增评审状态：AI 生成的用例初始状态为 `待评审`，人工审核通过后，状态改为 `未执行`，正式入库可执行，避免错误用例入库。

##### [2.2.1.3](2.2.1.3) API 契约库（API Contract Library）

核心目标：对接 Swagger/OpenAPI，存储接口的标准化契约，为 API 自动化测试、AI 生成接口用例提供支撑。

- 契约结构：接口 ID、接口路径、请求方法（GET/POST/PUT/DELETE）、请求参数（Query/Body/Header）、响应参数、状态码、接口描述、所属模块。

- 自动同步：支持定时同步 Swagger 接口文档，若接口变更，自动更新 API 契约，并同步关联的 API 用例，减少人工维护成本。

##### [2.2.1.4](2.2.1.4) 数据模板库（Data Template Library）

核心目标：存储测试过程中需要用到的各类数据，支持参数化、动态生成，提升用例的灵活性和复用性，同时支持敏感数据脱敏。

- 模板类型：预置测试数据（如管理员账号、测试账号）、参数化模板（如随机手机号、随机 ID）、响应断言模板（如预期响应结果）。

- 脱敏规则：内置手机号、身份证、邮箱等通用脱敏规则，也支持自定义脱敏，生成测试数据时自动脱敏，避免明文存储敏感数据，符合合规要求。

- 关联使用：用例步骤可引用数据模板，实现测试数据的统一管理，避免用例中硬编码数据。

##### [2.2.1.5](2.2.1.5) 标签体系（Tag System）

核心目标：为所有测试资产（用例、页面对象、API 契约、数据模板）提供统一标签，支持快速筛选、分类、批量操作。

- 标签类型：业务标签（如：登录、下单）、优先级标签（P0/P1/P2/P3）、测试类型标签（冒烟 / 回归 / 功能）、模块标签（用户中心 / 商品模块）。

- 关联规则：一个资产可关联多个标签，支持按标签筛选资产（如筛选 “P0 + 登录 + Web” 的用例）。

##### [2.2.1.6](2.2.1.6) 权限与多租户模块（新增，企业级基础能力）

核心目标：解决团队协作的数据隔离、权限管控问题，避免数据混流、越权操作。

- 多租户隔离：支持不同业务线 / 团队的租户隔离，租户间数据完全独立，避免互相干扰；

- RBAC 权限体系：内置标准角色，支持自定义角色：

|    角色|    权限说明|
|---|---|
|    平台管理员|    全平台所有权限|
|    项目负责人|    项目内所有资源的管理权限|
|    测试人员|    用例编辑、执行、查看权限|
|    研发人员|    用例、执行结果只读权限，无修改权限|
|    访客|    只读权限|
- 数据权限：支持按项目、模块控制资源的可见性，比如 A 团队看不到 B 团队的用例 / 页面对象。

### 2.3 AI 编排层（智能化核心层，依赖测试资产中心）

核心目标：基于测试资产中心的资产，实现测试全流程智能化，减少人工干预，提升测试效率，同时确保 AI 生成的内容可执行（依赖页面对象 / API 契约）。

关键纠正：**AI 只负责 “业务编排”，不负责 “技术实现”**（不生成定位器、不生成底层代码），所有技术相关的依赖均来自测试资产中心，解决当前 AI 生成用例无法执行的问题。

#### 2.3.1 各 Agent 详细设计

##### [2.3.1.1](2.3.1.1) 需求解析 Agent

- 核心功能：解析输入源层的多源数据（PRD、缺陷单、线上日志等），提取业务规则、页面信息、元素信息、接口信息，输出标准化的业务结构。

- 输出格式（对接测试资产中心）：

```json

{
  "page_name": "登录页面",
  "page_code": "LoginPage",
  "module_name": "用户中心",
  "test_points": ["用户名输入框输入内容", "密码输入框输入内容", "点击登录按钮", "登录成功跳转到首页"],
  "elements": ["用户名输入框", "密码输入框", "登录按钮"],
  "api_list": []
}
```

- 核心依赖：测试资产中心的页面对象库（校验解析出的页面 / 元素是否已存在）、API 契约库（校验接口是否已存在）。

##### [2.3.1.2](2.3.1.2) 测试设计 Agent

- 核心功能：基于需求解析 Agent 的输出，结合测试资产中心的页面对象、API 契约，生成测试点、测试用例、测试场景，确保用例可执行。

- 核心逻辑：

    1. 匹配测试资产中心的页面对象（通过 page_code），获取页面下的元素列表；

    2. 结合业务规则，生成测试步骤（动作 + 元素 + 数据，元素关联 element_code，不存储定位器）；

    3. 生成预期结果（基于业务规则，如 “登录成功后跳转到首页”）；

    4. 自动关联数据模板（如用户名 / 密码数据）；

    5. 生成的用例初始状态为 `待评审`，进入人工复核流程。

- 输出：标准化测试用例（存入用例库，待评审）、测试场景（多用力组合）。

##### [2.3.1.3](2.3.1.3) 脚本生成 Agent

- 核心功能：读取测试资产中心的页面对象（元素定位器）、API 契约，结合测试用例，生成可直接执行的自动化脚本（Python+Playwright for Web；Requests for API）。

- 核心逻辑：

    1. 从用例中获取 page_code、element_code，从页面对象库中获取元素定位器；

    2. 根据用例动作（input/click/assert_url 等），生成对应的 Playwright/Requests 代码；

    3. 脚本中引用页面对象库的定位器，不硬编码定位器，确保元素变更后脚本无需修改。

- 输出：可执行自动化脚本（存入用例库，关联对应用例）。

##### [2.3.1.4](2.3.1.4) 失败归因 Agent

- 核心功能：结合证据采集层的执行数据（截图、日志、Trace），自动定位用例失败原因，区分 “元素失效”“业务逻辑异常”“环境问题”“脚本问题”。

- 核心逻辑：

    1. 若失败原因是 “元素未找到”，自动校验页面对象库中该元素的健康状态，若失效，提示 “元素失效，请更新定位器”；

    2. 若失败原因是 “接口响应异常”，关联 API 契约，校验接口参数、响应格式是否匹配；

    3. 输出失败归因报告，给出优化建议（如 “更新元素定位器”“检查接口参数”）。

- 核心依赖：证据采集层的执行数据、测试资产中心的页面对象库、API 契约库。

##### [2.3.1.5](2.3.1.5) 风险评估 Agent

- 核心功能：基于质量分析层的结果、测试用例执行情况、缺陷数据，对模块 / 版本进行风险评分，识别高风险点。

- 评估维度：用例通过率、Flaky 用例数量、缺陷密度、元素失效数量、核心功能覆盖情况。

- 输出：风险评分（0-100 分）、风险报告、高风险点建议（如 “登录模块元素失效较多，需优先修复”）。

##### [2.3.1.6](2.3.1.6) 用例评审流程（新增，质量管控）

- AI 生成用例后，自动进入待评审状态，通知测试负责人进行复核；

- 测试人员复核用例的业务逻辑、步骤正确性，审核通过后，用例状态改为未执行，正式入库；

- 审核不通过的用例，打回 AI 重新生成，留存评审记录，可追溯。

#### 2.3.2 核心依赖与输出

- 依赖：测试资产中心的所有资产（页面对象、用例、API 契约、数据模板）、输入源层的原始数据、证据采集层的执行数据。

- 输出：可执行自动化脚本、测试场景、失败归因报告、风险评估报告，供自动化执行层、质量分析层调用。

### 2.4 自动化执行层（执行核心层，依赖测试资产中心 + AI 编排层）

核心目标：执行 AI 编排层生成的自动化脚本，实现 Web/API/Mobile 多端自动化测试，依赖测试资产中心的页面对象、API 契约，确保执行稳定、准确。

#### 2.4.1 各执行模块详细设计

##### [2.4.1.1](2.4.1.1) Web 自动化（核心，依赖页面对象库）

- 内核：Playwright（支持 Chrome/Firefox/Edge，稳定性优于 Selenium）。

- 核心逻辑：

    1. 从 AI 编排层获取自动化脚本，或从用例库读取用例，动态加载页面对象库的元素定位器；

    2. 执行脚本：打开页面（基于 page 表的 url）、操作元素（基于 element 表的定位器）、执行断言；

    3. 若元素定位失败，自动尝试备用定位器；若备用定位器也失败，标记元素失效，并触发失败归因 Agent。

- 核心依赖：测试资产中心的页面对象库（元素定位器）、AI 编排层的自动化脚本。

##### [2.4.1.2](2.4.1.2) API 自动化（依赖 API 契约库）

- 内核：Requests（Python），支持 RESTful API、GraphQL API。

- 核心逻辑：

    1. 从 AI 编排层获取 API 自动化脚本，或从用例库读取 API 用例；

    2. 从 API 契约库获取接口路径、参数模板，动态填充测试数据（来自数据模板库）；

    3. 发送请求，校验响应结果（与预期结果、API 契约对比）；

    4. 记录接口响应日志、状态码，供证据采集层采集。

- 核心依赖：测试资产中心的 API 契约库、数据模板库、AI 编排层的自动化脚本。

##### [2.4.1.3](2.4.1.3) Mobile 自动化（可扩展）

- 内核：Appium + Playwright（小程序），支持 Android/iOS APP、小程序。

- 核心逻辑：参考 Web 自动化，扩展页面对象库，支持 Mobile 元素的录制、定位（如坐标定位、ID 定位），实现 Mobile 端用例的自动化执行。

- 核心依赖：测试资产中心的页面对象库（Mobile 元素）、AI 编排层的自动化脚本。

#### 2.4.2 核心依赖与输出

- 依赖：AI 编排层的自动化脚本、测试资产中心的页面对象库、API 契约库、数据模板库、执行与调度中心的调度指令。

- 输出：用例执行结果（通过 / 失败 / 阻塞）、执行日志、失败截图 / 录屏，供证据采集层、质量分析层调用。

### 2.5 执行与调度中心（调度核心层）

核心目标：对自动化执行层的任务进行统一调度、管理，保障测试任务高效、稳定执行，提升资源利用率，支持大规模测试任务并发执行。

#### 2.5.1 核心功能详细设计

- **CI/CD 集成**：对接 GitLab/GitHub、Jenkins 等工具，支持代码提交、版本发布时自动触发测试任务（如冒烟测试、增量回归），实现 “代码提交→自动测试→结果反馈” 的闭环。

- **并发调度**：基于 K8s 实现任务并发执行，根据任务优先级、资源占用情况，动态分配执行节点，避免资源浪费，提升测试效率（如同时执行 100 条 Web 用例）。

- **环境分配**：支持多环境隔离（测试环境、预发环境、生产环境），用户可指定测试环境，调度中心自动分配对应环境的执行节点，确保测试环境一致性。

- **重试策略**：支持分级重试（如普通用例失败重试 1 次，P0 用例失败重试 2 次），可配置重试条件（如元素未找到、网络超时可重试，业务逻辑失败不重试），提升用例执行通过率。

- **任务管理**：支持测试任务的创建、启动、暂停、终止，查看任务执行进度、资源占用情况，支持任务优先级设置（P0>P1>P2>P3）。

#### 2.5.2 核心依赖与输出

- 依赖：自动化执行层的执行能力、基础设施层的容器资源（Docker/K8s）、测试资产中心的用例（任务来源）。

- 输出：任务调度结果、执行状态、资源占用情况，供质量分析层、发布决策层调用。

### 2.6 证据采集层（数据支撑层）

核心目标：采集自动化执行过程中的全量数据，为失败归因、质量分析提供客观、全面的证据，确保问题可复现、可追溯。

#### 2.6.1 核心采集内容详细设计

- **Trace 追踪**：采集用例执行全链路数据（步骤执行顺序、执行时间、调用的页面对象 / 元素、接口请求），形成执行链路图，便于定位执行卡点。

- **Screenshot**：Web/Mobile 用例执行过程中，自动截图（如每步截图、失败时截图），截图关联用例步骤、执行时间，存储到 MinIO，供人工查看、失败复现。

- **Video**：支持用例执行过程录屏（可配置开启 / 关闭），针对复杂失败场景，便于完整复现执行过程，定位问题原因。

- **Console 日志**：采集浏览器控制台日志（如 JS 报错、警告），用于定位 Web 前端相关的失败原因（如前端脚本报错导致元素无法点击）。

- **Network 日志**：采集 Web/API 执行过程中的网络请求日志（请求 URL、参数、响应、状态码、耗时），用于定位接口调用失败、网络超时等问题。

- **系统 Logs**：采集平台自身日志（执行引擎日志、调度日志、数据库日志），用于定位平台自身异常（如数据库连接失败、执行节点宕机）。

#### 2.6.2 核心依赖与输出

- 依赖：自动化执行层的执行数据、执行与调度中心的任务信息。

- 输出：全量执行证据（截图、录屏、日志、Trace），供 AI 编排层（失败归因 Agent）、质量分析层调用。

### 2.7 质量分析与洞察层（分析决策层）

核心目标：基于证据采集层的全量数据，进行多维度分析，输出质量报告、优化建议，为发布决策提供数据支撑，提升测试质量。

#### 2.7.1 核心分析功能详细设计

- **Flaky 用例分析**：识别不稳定用例（同一用例多次执行，时而通过、时而失败），分析失败原因（如元素定位不稳定、网络波动、环境问题），给出优化建议（如更换更稳定的定位器、增加等待时间）。

- **失败聚类**：将失败用例按失败原因（如元素失效、接口报错、业务逻辑异常）、所属模块、所属页面进行聚类，定位共性问题（如 “登录页面多个元素失效，可能是前端版本更新导致”）。

- **趋势分析**：统计测试通过率、用例覆盖率、缺陷密度、元素失效数量等指标的变化趋势（日 / 周 / 月），识别质量下降风险（如通过率突然下降，需排查近期代码变更、环境变更）。

- **风险评分**：结合用例通过率、Flaky 用例数量、缺陷密度、元素健康状态等维度，对每个模块 / 版本进行风险评分（0-100 分），区分高风险、中风险、低风险模块。

#### 2.7.2 核心依赖与输出

- 依赖：证据采集层的全量执行证据、测试资产中心的用例 / 页面对象 / 缺陷数据、AI 编排层的失败归因报告。

- 输出：质量分析报告、Flaky 用例列表、失败聚类报告、趋势图表、风险评分，供发布决策与治理层调用。

### 2.8 发布决策与治理层（顶层决策层）

核心目标：基于质量分析与洞察层的结果，实现测试门禁管控，给出发布决策建议，确保发布质量，降低线上风险。

#### 2.8.1 核心功能详细设计

- **PR 门禁**：代码合并前，自动触发冒烟测试（执行核心用例），若测试不通过（如核心用例失败、风险评分过低），拦截 PR 合并，避免缺陷引入主干分支。

- **冒烟门禁**：版本发布前，执行冒烟用例（覆盖核心功能），确保核心功能可用，若冒烟用例失败，禁止版本发布，需修复缺陷后重新测试。

- **回归门禁**：版本迭代后，执行回归用例（覆盖历史功能），防止回归缺陷，若回归用例通过率低于阈值（如 95%），需排查回归缺陷，重新测试。

- **自动缺陷创建**：测试用例执行失败后，自动将失败信息（步骤、截图、日志）整理成缺陷单，自动创建到 Jira / 禅道，分配给对应研发负责人，打通测试到缺陷的闭环。

- **风险放行建议**：基于质量分析层的风险评分，给出发布 / 拦截建议（如 “风险评分 85 分，核心功能无缺陷，建议放行”“风险评分 60 分，登录模块元素失效较多，建议拦截，修复后重新测试”）。

#### 2.8.2 核心依赖与输出

- 依赖：质量分析与洞察层的质量报告、风险评分、失败聚类报告。

- 输出：发布决策结果、放行建议，反馈给研发、测试团队，指导版本发布。

### 2.9 基础设施层（支撑层，保障平台稳定运行）

核心目标：为整个平台提供底层支撑，确保平台高可用、可扩展、可维护，支撑大规模测试任务的执行。

#### 2.9.1 核心组件详细设计

- **Docker + K8s**：实现容器化部署，将平台各模块（前端、后端、执行引擎、数据库）打包为 Docker 镜像，通过 K8s 实现容器编排、弹性扩展、负载均衡，确保环境一致性，提升平台稳定性。

- **配置中心**：统一管理平台所有配置（数据库配置、执行配置、环境配置、告警配置），支持配置动态更新，无需重启平台，提升维护效率。

- **存储中心**：

    - MySQL：存储结构化数据（页面对象、用例、API 契约、用户信息、执行结果、审计日志等）；

    - MinIO：存储非结构化数据（截图、录屏、日志、文档等），支持高可用、可扩展。

- **消息队列（如 RabbitMQ/Kafka）**：解耦执行调度、日志采集、AI 编排等模块，实现异步通信，提升平台吞吐量，避免模块之间相互阻塞。

- **监控告警**：基于 Prometheus + Grafana，监控平台运行状态（CPU、内存、磁盘占用）、执行任务状态（执行成功率、任务耗时）、元素健康状态，设置告警阈值，若出现异常（如执行节点宕机、元素失效过多），通过邮件、钉钉 / 企业微信发送告警，及时通知运维、测试人员处理。

#### 2.9.2 核心依赖与输出

- 依赖：无（底层支撑，为所有上层模块提供服务）。

- 输出：稳定的运行环境、资源支撑、监控告警服务，保障整个平台正常运行。

## 三、当前平台偏离方向的核心原因及纠正方案

### 3.1 核心偏离原因

1. **优先级倒置**：先建设 AI 编排层、执行层、调度层，未优先建设测试资产中心（尤其是页面对象模块），导致上层模块缺乏核心依赖，无法落地执行（如 AI 生成的用例无元素可操作，执行引擎无定位器可调用）。

2. **AI 定位错误**：让 AI 负责生成技术细节（如定位器、代码），而非只负责业务编排，导致 AI 生成的用例与实际页面脱节，无法执行。

3. **层间依赖混乱**：未明确各层的依赖关系，导致测试资产中心与 AI 编排层、执行层无法有效联动，架构空转。
