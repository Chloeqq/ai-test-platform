# 系统架构现状 vs 目标架构差距分析

> 日期: 2026-07-12
> 方法: 3 个 agent 并行追踪 Full Call Chain，逐文件/逐函数/逐行号对比目标架构图

---

## 一、总体判断

**当前系统有两条并行路径，但它们不是目标架构中的"A 路径(显式 steps_hint) → validate → 进入编排层"和"B 路径(自然语言) → structurer → 进入编排层"。实际情况更复杂：**

| 架构图节点 | 实际状态 | 差距 |
|-----------|---------|------|
| 统一入口 `SPLIT{输入类型判断}` | ❌ 不存在 | 两套独立的入口函数,无统一路由 |
| A 路径 `resolve_explicit_step` | ✅ 存在 | 仅被 orchestrator/generate_pipeline 调用,不在 web-ui 主流程 |
| B 路径 `structured_steps_from_candidate` | ✅ 存在 | 两个调用点(build_point + _steps_from_candidate),参数不同 |
| 编排层富化 `ENRICH` | ⚠️ 部分存在 | 仅 Path B(_steps_from_candidate)有 Behavior Registry fallback; Path A(build_point)缺失 |
| `build_point`(canonical builder) | ⚠️ 存在但非唯一 | build_point 用于 Path A; `_manual_point_from_candidate` 用于 Path B |
| 人工编辑不回灌 | ✅ 正确 | upsert 路径不调 build_point |

## 二、逐层调用链(当前实际代码)

### Layer 1: 入口 — 两条独立路径,无统一路由

```
前端 UI
  │
  ├── Path A: "保存测试点" 按钮 → POST /api/workbench/test-point-assets/save
  │     → SaveTestPointAssetsService.execute()
  │       → build_point(candidate) × N       ← 唯一入口,无"输入类型判断"
  │         → structured_steps_from_candidate()  ← 总是走 B 路径(structurer)
  │         → assertion_count == 0 → 仅加 warning
  │         ★ 不调用 Behavior Registry(resolve_and_compile)
  │
  └── Path B: "编辑/手动创建" → POST/PUT /api/workbench/test-point-assets[/{id}]
        → WorkbenchFacade.upsert_test_point_asset()
          → _manual_point_from_candidate()
            → _steps_from_candidate(db=db)
              → structured_steps_from_candidate()  ← B 路径(structurer)
              → assertion_count == 0 + db != None
                → resolve_and_compile()  ← ★ 唯一有 Behavior Registry fallback 的地方
```

## 三、与目标架构图的关键差距

| # | 目标架构节点 | 当前状态 | 差距描述 |
|---|-------------|---------|---------|
| 1 | 统一入口 `SPLIT` | ❌ 不存在 | Path A(`save_test_point_assets_service`)和 Path B(`facade_test_point_assets.upsert`)是两套独立入口,无统一路由 |
| 2 | `resolve_explicit_step` 作为 A 路径 | ⚠️ 存在但架空 | 仅在 orchestrator 和 direct-candidate 流程使用,web-ui 的 AI save 流程(Path A)不走它 |
| 3 | `ENRICH` 编排层富化 | ⚠️ 仅 Path B | `_steps_from_candidate`(Path B)有 Behavior Registry fallback; `build_point`(Path A)没有 |
| 4 | `build_point` 为唯一 canonical builder | ❌ 不唯一 | `_manual_point_from_candidate` 是第二套 builder,两套逻辑未统一 |
| 5 | `ASSERT_CHECK` 在 ENRICH 中 | ⚠️ 仅 Path B | Path A 的 assertion_count==0 仅加 warning,不尝试 resolve_and_compile |
| 6 | `REGISTRY` 查询 | ⚠️ 仅 Path B | Path A 缺失此能力 |
| 7 | 人工编辑不回灌 | ✅ 正确 | upsert 路径不调 build_point,符合目标 |
| 8 | `BUILD_CHECK`(已有 structured_steps?) | ⚠️ 分布式 | 实际代码在多个调用点各自判断,无统一 BUILD_CHECK |
| 9 | `compile_execution_steps` | ✅ 存在 | 纯编译函数,调用者负责 review 过滤 |

## 五、修复建议(按优先级)

### P0 — 统一 Path A 和 Path B 的 Behavior Registry 回退

**问题**: Path A(`build_point`)没有 Behavior Registry fallback,导致 AI 生成的测试点缺少断言。

**修复**: 在 `build_point` 或 `SaveTestPointAssetsService` 中添加 db 参数,当 `assertion_count==0` 时调用 `resolve_and_compile`。

**工作量**: ~2h

### P1 — 统一 builder 入口

**问题**: `build_point`(Path A)和 `_manual_point_from_candidate`(Path B)是两套独立的 point 构建逻辑。

**修复**: 让 `_manual_point_from_candidate` 也调用 `build_point`,或在 `build_point` 中加入 DB 参数使其成为唯一入口。

**工作量**: ~3h

### P2 — 统一结构化调用

**问题**: `structured_steps_from_candidate` 在两个位置被调用,参数不同(resolver/page_hook 在 Path B 为 None)。

**修复**: Path B 也传入 resolver/page_hook,或统一到一个调用点。

**工作量**: ~1h
