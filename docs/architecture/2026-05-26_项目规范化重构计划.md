
# 项目规范化重构计划

## Context

当前项目最影响日常开发的问题是 `apps/web-ui-service/app/api/workbench/facade.py` 膨胀到 4,406 行，WorkbenchFacade 单个类 2,657 行、53 个公开方法 + ~70 个私有方法，每次改功能都要在这个文件里挣扎。其他架构问题（Repository 缺失、DB 模式不统一、session 管理混乱）是更深层的债，但先解决最痛的那个。

约束：最小侵入（不改接口签名、不改 Router 返回值）、边重构边补测试。

## 总体策略：分 4 期，每期可独立交付

---

## 第 0 期（先止血，1-2 天）

在动代码之前，先解决几个不涉及逻辑、但影响仓库健康的问题：

### 0.1 Git 仓库瘦身
- 把 `actions-runner/`（1.3GB）移出仓库，加到 `.gitignore`
- 修复 `.gitignore` 中 `node_modules` 的路径，确保覆盖 `apps/web-ui-service/frontend/node_modules/`
- 用 `git rm --cached` 移除已跟踪的二进制文件（`.webm` 视频、`dev.db`、`*.jsonl` 日志）
- 确认 `.env` 在 `.gitignore` 中且未被跟踪

### 0.2 安全清理
- 确认 `.env` 中的 Volcengine API key 未被提交到 git 历史（如已提交，轮换 key）
- `docker-compose.override.yml` 中的默认密码（`change-me`、`admin123`）替换为占位符并加注释说明
- 清理 root 的 `_add_agent_comments.py`（一次性脚本）

### 0.3 清理死引用
- 移除 root `package.json` 中指向不存在的 `apps/web-console/static/app.js` 的脚本
- 移除 `Makefile` 中对应的 `check:console` 目标

## 第 1 期（facade.py 拆分，5-7 天）

核心原则：**只移动代码，不改行为**。先写特征测试锁定现有行为，再拆分，测试应全程绿灯。

### 1.1 特征测试（Characterization Tests）

为 WorkbenchFacade 的每个公开方法写特征测试，不关心"对不对"，只关心"现在返回什么"：

```
apps/web-ui-service/tests/unit/test_workbench_facade.py
```

测试策略：
- 用 `pytest` mock `Session` 和各个 service 依赖
- 每个测试直接调 facade 方法，断言返回结构的 shape（不关心具体值）
- 覆盖按领域分组：dashboard、test_point_assets、case_generation、review、governance、runs
- 这些测试不追求覆盖率，追求"改完代码后行为不变"的安全网

### 1.2 识别 facade.py 中的内聚模块

扫描 facade.py 的方法和私有函数，按领域分组：

| 领域 | 预估方法数 | 目标文件 |
|------|-----------|---------|
| Dashboard | ~12 个公开方法 | `app/services/workbench_dashboard_service.py`(已有部分逻辑可复用) |
| Test Point Assets | ~15 个公开方法 | `app/services/workbench_asset_service.py`(已有，迁移 facade 中的逻辑过去) |
| Case Generation | ~8 个公开方法 | 已有 `workbench_generation_service.py`，迁移 facade 中的编排逻辑过去 |
| Review & Governance | ~6 个公开方法 | 已有 `workbench_governance_service.py` 和 `workbench_review_service.py` |
| Runs & Runtime | ~5 个公开方法 | 已有 `workbench_runtime_service.py` |
| Utility helpers | ~40 个私有方法 | `app/api/workbench/_helpers.py`(纯函数：文件读写、格式转换、安全回滚) |

关键观察：很多"领域 service"其实已经存在（asset_service、governance_service 等），facade 里的逻辑是**重复编排**，可以直接删掉 facade 中的逻辑，让 facade 方法变成对已有 service 的薄调用。

### 1.3 拆分步骤（按方法，一个方法一个 PR）

每个方法按以下流程操作：

1. 在对应领域 service 中创建同名函数，接收相同参数（加上 `db: Session`）
2. 将 facade 方法体中的逻辑**整体搬过去**，不改一行逻辑
3. facade 方法变成一行代理：`return some_service.some_method(db, **params)`
4. 运行特征测试确认行为不变

优先级排序（按文件行数从大到小）：

1. **`dashboard_overview()`**（202 行）→ 已有 `workbench_governance_service.py`，迁移过去
2. **`generate_cases_from_test_point_assets()`**（195 行）→ 已有 `workbench_generation_service.py`
3. **`list_test_point_reviews()`**（162 行）→ 已有 `workbench_review_service.py`
4. **`cleanup_case_consistency()`**（132 行）→ 已有 `workbench_case_consistency_service.py`
5. **`dashboard_governance()`**（128 行）→ 已有 `workbench_governance_service.py`

### 1.4 提取纯工具函数

facade.py 中的 `_` 前缀私有方法（约 40 个），很多是纯数据转换、文件 I/O、格式映射：

```python
# 示例：这些不依赖任何 service/db，直接提取到 _helpers.py
_normalize_xxx()
_safe_rollback_or_invalidate()
_read_json_file()
_write_json_file()
_build_test_point_script_preview()
_selenium_by_expression()
```

提取到 `app/api/workbench/_helpers.py`，保持原函数名不变。

### 1.5 第 1 期完成标准

- facade.py < 800 行（每个方法 ≤ 5 行代理代码）
- 所有公开方法的特征测试通过
- Router 层零改动
- `python -m pytest apps/web-ui-service/tests/ -x` 全绿

## 第 2 期（Repository 层引入，3-5 天）

第 1 期完成后，service 层的职责变得清晰，再引入 Repository 层隔离数据库访问。

### 2.1 Repository 基类

```python
# apps/web-ui-service/app/repositories/base.py
class BaseRepository:
    def __init__(self, db: Session):
        self.db = db
```

### 2.2 按聚合根创建 Repository

一次只迁移一个聚合根：

| Repository | 对应模型 | 迁移来源 |
|-----------|---------|---------|
| `TestPointRepository` | TestPoint, TestPointAsset | asset_service, facade |
| `TestCaseRepository` | TestCase, TestStep | test_case_service |
| `PageObjectRepository` | PageObject, PageElement | page_object_service |
| `ExecutionRepository` | TestCaseExecution | runtime_service |

每个 Repository 只包含 CRUD + 按模型聚合的查询方法。不从 service 中搬业务逻辑。

### 2.3 迁移一个 service 验证模式

选择 `test_case_service.py` 作为第一个迁移目标（它是最大的 service 文件之一），将其中的 `db.execute(select(...))` 替换为 `self.repo.xxx()`。验证模式可行后再推广。

### 2.4 第 2 期完成标准

- 所有 `db.execute()` 调用都在 Repository 类中，service 不再直接操作 SQLAlchemy Session
- 新增的 Repository 有独立的单元测试
- Service 层可以通过 mock Repository 进行单元测试

## 第 3 期（统一模式，2-3 天）

### 3.1 统一 Service 实例化

当前三种模式：模块级函数、工厂函数、类 + 构造函数。统一为：

```python
class SomeService:
    def __init__(self, db: Session, repo: SomeRepository):
        self.db = db
        self.repo = repo
```

不使用 DI 框架（避免引入新依赖），通过 FastAPI `Depends` 在 Router 层组装。

### 3.2 解决 Session 管理混乱

明确规则：
- **Router 层**通过 `Depends(get_db)` 获取 session
- **Service/Repository 层**只接收 db 参数，绝不自己 `SessionLocal()`
- 删除 `workbench_state_store.py`、`service.py`、`facade.py`、`generate_pipeline.py` 中所有 `SessionLocal()` 自创建调用

### 3.3 ai-orchestrator 的 raw sqlite3

暂不处理（风险最高，且不在日常工作流中）。建议独立开一个 Issue 跟踪。

## 验证策略

每期每步的验证方式：

1. **每一个 PR 合并前**：`python -m pytest apps/web-ui-service/tests/ -x` 全绿
2. **第 1 期每拆一个方法后**：启动 API server 和前端，手动验证对应页面功能正常
3. **每期结束后**：运行 `make test` 全量测试 + `make static-baseline` 静态检查
4. **回归保护**：第 1 期写的特征测试永久保留，后续重构以此为准

## 不做的事（明确边界）

- **不处理 ai-orchestrator 的重构**：它是 Flask 应用，与 web-ui-service 问题模式不同，分开计划
- **不引入 DI 框架**：避免给项目增加陌生依赖
- **不合并或删除数据库**：只改代码组织结构，不动数据模型
- **不碰 `shared_backend`**：它是共享层，改动影响两个 app，不安全
- **不改 Router 接口**：URL、请求/响应格式完全不动
