## 二、任务 1：Risk Classifier（自动判定规则引擎）

### 要做什么

在 Layer Comparator 之后，增加一个规则引擎。Comparator 发现"不一致"，Classifier 判断"这个不一致的风险等级是什么，能不能自动判定"。

### 输入

```text
LayerComparator 的输出：
  - intent_name: "登录_错误密码"
  - divergences: [{
      direction: "intent_ui",
      description: "UI期望'请输入账号'，API返回'密码不正确'",
      possible_causes: ["A) AI推测错误", "B) 文案不匹配", "C) 系统变更"]
    }]
  - api_result: {status: "passed", assertions: [passed, passed, passed]}
  - ui_evidence: {status: "passed", assertions: [{target: "login-submit-btn", ...}]}
```

### 输出

```text
RiskClassified:
  - risk_level: "HIGH"  ← 之前这里永远是"需人工判断"
  - reasons: ["断言目标为button而非error元素", "API message与UI expected不一致"]
  - evidence: ["API: message='密码不正确'", "UI: target=login-submit-btn"]
  - auto: true           ← 自动判定，不需要人工
  - confidence: 0.88
```

### 规则清单（5 条自动规则）

| # | 规则名称 | 判定条件 | 风险等级 | 自动? | 置信度 |
|---|---------|---------|---------|------|--------|
| R1 | zero_assertion | UI 断言数为 0 | CRITICAL | ✅ 自动 | 1.0 |
| R2 | button_as_error_target | 断言目标后缀为"-btn" 且 期望值含中文错误语义 | HIGH | ✅ 自动 | 0.92 |
| R3 | api_ui_message_mismatch | API message ≠ UI expected（且都是错误消息） | HIGH | ✅ 自动 | 0.85 |
| R4 | backend_failure_ui_pass | API 断言失败 + UI 状态=passed + UI 无有效断言 | CRITICAL | ✅ 自动 | 0.95 |
| R5 | multi_source_mismatch | API 通过 + DB 无记录（或反之） | HIGH | ✅ 自动 | 0.88 |

```text
无规则命中 → risk=MEDIUM, auto=false（需人工）

预期结果：
  24 条历史审计用例中：
  - R1 命中: ~3 条 (零断言) → 自动 CRITICAL
  - R2 命中: ~10 条 (按钮目标错误) → 自动 HIGH
  - R3 命中: ~5 条 (文案不匹配) → 自动 HIGH
  - R4 命中: ~2 条 (后端失败UI假通过) → 自动 CRITICAL
  - 无命中: ~4 条 → 需人工 MEDIUM
  
  自动判定率: 20/24 = 83% → 远超 30% 目标
```

### 验收标准

```text
✅ R1 zero_assertion: 100% 命中率（3/3 条零断言案例）
✅ R2 button_as_error_target: >80% 命中率（>8/10 条按钮目标案例）
✅ R3 api_ui_message_mismatch: >80% 命中率
✅ R4 backend_failure_ui_pass: >90% 命中率
✅ 自动判定率 > 30%（目标：83%）
✅ 无规则命中时仍输出"需人工"（不降低可靠性）
```

## 三、任务 2：Evidence Graph（多源交叉验证）

### 要做什么

不再用单一 API 作为 Oracle。API 结果和 DB 结果互相验证。两个独立源同时正确 = 高可信。两个独立源不一致 = 报告冲突。

### 交叉验证矩阵

```text
API 结果        DB 结果        判定
──────────────────────────────────────────
token 存在     session 存在    ✅ aligned
token 存在     session 不存在  🚨 api_db_divergence（高可信的证据冲突）
error 返回     session 不存在  ✅ aligned
error 返回     session 存在    🚨 data_consistency_error（逻辑矛盾）
请求超时       —               ⚠️ network（不做交叉验证）
平台异常       —               ⚠️ platform（不做交叉验证）
```

### 对 Layer Comparator 的影响

```text
之前：
  LayerComparator 输入: intent + API_result + UI_evidence
  对比维度: intent_api, intent_ui

之后：
  LayerComparator 输入: intent + API_result + DB_evidence + UI_evidence
  对比维度: intent_api, intent_ui, api_db_cross

  新增 api_db_cross：
    - API+DB 一致 + UI 不一致 → 高置信 UI 问题
    - API+DB 不一致 → 所有相关判定降低置信度
```

### 验收标准

```text
✅ 当 API+DB 一致时，UI divergence 的 confidence > 0.85
✅ 当 API+DB 不一致时，UI divergence 的 confidence < 0.50 且标记 api_db_conflict
✅ DB 证据缺失时不影响现有逻辑（降级处理）
```

## 四、任务 3：UIEvidence 字段扩展

### 要做什么

不开发 UI Runner。只扩展 UIEvidence 数据模型，增加 5 个可选字段。这些字段由外部系统填充，ATP 只消费。

### 新增字段

| 字段 | 类型 | 必填 | 用途 |
|------|------|------|------|
| screenshot_url | string | 否 | 失败时的页面截图。Classifier 在 wrong_target 命中时引用 |
| dom_snapshot | string | 否 | 失败时的可访问性树/or HTML片段。验证"目标元素是否存在" |
| trace_url | string | 否 | Playwright trace 文件路径。回溯完整的执行过程 |
| network_logs | list | 否 | API 调用日志。验证前端是否发出了正确的 API 请求 |
| console_logs | list | 否 | 浏览器控制台错误。区分"断言失败"和"页面 JS 崩溃" |

### 对 Risk Classifier 的影响

```text
R2 (button_as_error_target) 增强：
  - 如果 dom_snapshot 存在 → 搜索是否有 role=alert/toast 的元素
    → 有 → confidence 从 0.92 提升到 0.98
    → 无 → 维持 0.92

R4 (backend_failure_ui_pass) 增强：
  - 如果 network_logs 存在 → 检查前端是否发出了 API 请求
    → 发出了 → 前端静默吞了错误 → CRITICAL
    → 未发出 → 前端根本没有调用 → 这是更严重的问题

R3 (api_ui_message_mismatch) 增强：
  - 如果 screenshot_url 存在 → Classifier 输出中引用截图路径
    → 用户直接看到"文案确实不匹配"的证据
```

### 验收标准

```text
✅ UIEvidence 模型新增 5 个可选字段
✅ 所有字段为空时不影响现有逻辑
✅ 至少 1 条 Risk Rule 能利用扩展字段提升置信度
✅ ATP 不产生这些数据 — 只消费
```
