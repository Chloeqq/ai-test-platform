## 一、总体目标

V3.0 不是"换一种 YAML 写法"，而是建立一套**可追溯、可编译、可执行、可诊断**的企业级测试 DSL。

| 目标 | 含义 |
|------|------|
| 业务可读 | 测试人员看到的是意图、场景、数据、断言，而不是 CSS 和 XPath |
| 执行稳定 | 元素定位从页面对象库动态解析，优先使用真实 `data-testid` |
| 生成可控 | 每条用例必须绑定 `source_asset_id + intent_id`，避免重复生成 |
| 断言可信 | `expected_result` 从自然语言编译成可执行 assertion |
| 报告专业 | Allure 展示业务树、步骤、数据摘要、断言、证据和失败原因 |
| 批量可治理 | 执行前判断哪些用例高概率成功、哪些缺数据或缺前置 |

核心设计理念：**语义表达 → 编译治理 → 执行证据** 三者打通。

## 三、四层架构

V3.0 引入编译分层，解决"语义表达 vs 机器执行"的鸿沟：

```
第 1 层：Source DSL      面向测试人员，表达业务语义
        identity / requirement / scenario / data / steps / assertions / evidence

          ↓ DSL Compiler 编译

第 2 层：Execution IR    已解析但未执行的动作
        标准动作、页面、元素编码、数据引用、断言类型、traceability、compiler_status

          ↓ Runner Adapter 适配

第 3 层：Runner Script   兼容当前 runner 的具体脚本
        goto / input / click / assert_url / assert_visible + locator_type / locator_value

          ↓ Runtime Engine 执行

第 4 层：Runtime Record  执行后的事实记录
        实际 locator、耗时、截图、视频、console、失败 step、失败分类、Allure 标签
```

**关键原则**：Runner 不需要直接理解 `semantic_action`，只执行编译后的具体动作。当前 V1.1 直接运行在第三层（Runner Script），跳过了前两层的编译。

## 四、V1.1 → V3.0 差距分析

### 字段级对照

| 层次 | V1.1 现状 | V3.0 目标 | 新增内容 |
|------|----------|----------|---------|
| 元数据 | `project/module/title` | `+ domain/sub_module/risk_level` | 领域分类、风险等级 |
| 场景 | `intent_id/intent_type` | `+ business_goal/test_type[]/risk_points[]` | 业务目标、风控点 |
| 角色 | 无 | `actors + role` | 完全新能力 |
| 环境 | 硬编码 `page_url` | `env/network_profile/feature_flags` | 多环境支持 |
| 前置条件 | 纯文本字符串 | 结构化 `setup_action + params` | 可执行 setup |
| 变量 | `{{var}}` 单层 | `$test_data.xxx.yyy` 两级 | 变量解析引擎 |
| 步骤 | `input/click/goto/wait` | `+ http_request + extract + condition` | API 调用、变量提取 |
| 断言 | `assert_visible/text/url` (仅 UI) | api/ui/db/business/ai_semantic/composite (6 种) | 多维度断言 |
| 覆盖 | `requirement.source_asset_id` | `requirement_ids[]/risk_points[]` | 需求追溯 |
| 可观测 | 隐式（pytest 约定） | 声明式 `observability` | 声明式配置 |
| 回滚 | 无 | `rollback actions` | 完全新能力 |

### 关键设计约束

- **元素定位不发散**：DSL 中只写 `locator: "username_input"`，由页面对象库解析为具体定位策略
- **敏感数据脱敏**：密码、token 类字段标记 `sensitive: true`，报告只展示脱敏摘要
- **语义动作编译**：`semantic_action: input_username` 编译为 `action: input` + 页面对象绑定
- **语义断言映射**：`semantic_assertion: login_success` 必须配置具体断言组合（URL/用户名展示/token 等）
- **不修改被测系统**：`http://localhost:5174/#/login` 保留为业务事实，不自动篡改

## 六、与虚假通过问题的关系

当前 24 条 login 用例虚假通过根因分布（2026-06-25 批量验证结果）：

```
67% — 断言弱 (只有 assert_url)        → 质量门 RULE_003 FATAL → 已上线拦截  ✅
33% — 数据缺失 (data 字段不完整)       → 质量门 RULE_002 ERROR + V1.3 subtype 自动推断 ✅
~15% — 前置条件不可执行 (纯文本)       → V2.0 preconditions 引擎 ✅ 已上线 (login/account_state/sql)
~10% — AI 幻觉/模板残留                → 质量门 RULE_016 (桩)
  4% — 步骤行为不匹配 (重复点击/超时)  → 质量门 RULE_011 WARNING ✅ 已上线
```

**最终结果 (2026-06-25)**：V1.2 质量门(17/17满格) + V1.3 结构化数据 + V2.0 preconditions + V2.5a locator归一化 + V2.5b 断言编译器 + 6条YAML收尾 + RULE_016/017 全部上线。**24 条 login 用例 ALL PASS (0 REJECT, 0 REVIEW)**。从最初 20 条虚假通过到全线通过。

**DSL 升级主要解决前置条件结构化问题（~15%），断言和数据完整性问题（83%+）靠质量门规则更高效。**
