# 需求到可执行用例全链路方案与现状（页面对象 / 元素 / 用例）

## 1. 文档目标

本文面向当前 AI 自动化测试管理平台，回答以下核心问题：

1. 需求测试点 + 页面对象，如何转化为可执行测试用例。
2. 当前项目已经实现到哪里、哪些能力是部分实现、哪些还缺。
3. 测试设计 Agent 是否参与补全/校验。
4. 用例列表页、用例详情页如何统一支持执行，且可成功调起执行页并跑通。
5. 是否已生成可执行 YAML 与可执行代码，以及各自产物位置。

---

## 2. 全链路分层（目标态）

### L0 输入层：需求与上下文
- 输入：`requirement` + 多源上下文（PRD/OpenAPI/git diff/user story/缺陷/日志）。
- 入口：
  - `POST /requirements/parse`
  - `POST /orchestrate`
  - `POST /api/workbench/preview-test-points`

### L1 解析层：Requirement Parser（LLM）
- 责任：把需求解析为结构化 `test_intents`（场景、优先级、步骤、预期、涉及元素）。
- 关键实现：
  - `agents/requirement-parser-agent/src/prompt.py`
  - `agents/requirement-parser-agent/src/agent.py`
  - `apps/ai-orchestrator/src/services/requirement_parse_support.py`
- 当前模式：支持强制 `REQUIREMENT_PARSER_MODE=llm`。

### L2 测试点矩阵层（业务可测点）
- 责任：对 `test_intents` 做清洗、去噪、场景归一、优先级归一、统计。
- 关键实现：
  - `apps/web-ui-service/app/services/workbench_generation_service.py`
  - `apps/web-ui-service/app/services/test_point_service.py`

### L3 页面对象层（PO）
- 责任：提供 PageObject + PageElement（`element_code + locator_type + locator_value`）。
- 关键实现：
  - `apps/web-ui-service/app/models/page_object.py`
  - `apps/web-ui-service/app/services/page_object_service.py`
  - `apps/web-ui-service/app/services/page_object_recorder_service.py`

### L4 设计层：测试设计 Agent
- 责任：将 requirement/design_input 产出 case yaml 骨架。
- 关键实现：
  - `apps/ai-orchestrator/src/services/agent_execution_support.py`
  - `generate_case()` 调用 `TestDesignAgent`，失败时有 fallback case。
- 结论：测试设计 Agent 已参与“生成与补全”，但 fallback 仍可能触发。

### L5 转换层：候选用例 -> 可执行步骤对象
- 责任：将 `test_intents`（precondition/steps/expected/involved_elements）映射为 execution steps。
- 关键实现：
  - `apps/web-ui-service/app/routers/workbench_generation.py`
  - `apps/web-ui-service/app/services/workbench_generation_service.py`

### L6 资产层：YAML / 脚本 / DB
- YAML：`assets/test-cases/*.yaml`
- 可执行脚本：`reports/executions/generated-scripts/*.generated.py`
- Case + Step 入库：
  - `test_cases`
  - `test_case_steps`

### L7 执行层：Run Queue + Playwright/Pytest
- 入口：
  - `POST /api/workbench/run`
  - 运行页：`/execution/runs`
- 关键实现：
  - `apps/web-ui-service/app/routers/workbench_runs.py`
  - `apps/web-ui-service/app/services/workbench_runtime_service.py`
- 执行产物：run log、artifacts、execution_record、report。

## 3. 当前实现状态（As-Is）

## 3.1 已完成

1. **需求解析 -> 测试点矩阵（LLM）**
   - 强制 LLM 通道可用，且 prompt 已强化细粒度与场景配额。
   - `test_intents` 已包含 `precondition/steps/expected_result/involved_elements`。

2. **候选用例保真**
   - `preview -> selected_candidates` 不再只保留标题，已保留：
     - `precondition`
     - `steps`
     - `expected`
     - `scene_type`
     - `test_data_type`
     - `involved_elements`

3. **页面元素绑定增强（本轮新增）**
   - 在 case 同步入库前，基于页面对象元素库对步骤做自动绑定：
     - 写入 `target=element:<element_code>`
     - 写入 `locator_type / locator_value`
   - 对步骤动作做归一（如 `custom_step` 推断为 `input/click/assert/navigate`）。

4. **步骤字段保留增强（本轮新增）**
   - `normalize_test_steps` 已保留 `locator_type / locator_value / expected_result`，避免落库时丢失执行关键信息。

5. **执行入口（列表页）**
   - 用例列表支持单条执行、批量执行，跳转到 `/execution/runs?case_ids=...`。

6. **产物链路**
   - YAML 生成：已具备。
   - 可执行代码生成：已具备（script-generation agent）。
   - 执行引擎调起：已具备（run queue -> pytest/playwright）。

## 3.2 部分实现 / 风险点

1. **强制 LLM 稳定性**
   - 在强制 LLM 模式下，偶发上游模型输出异常会导致 `preview` 失败（无规则兜底时更明显）。
   - 当前已通过超时参数放宽减轻，但需进一步做“LLM 修复重试”策略。

2. **元素绑定精度**
   - 已实现自动匹配，但复杂页面/多相似元素时仍需增强（建议引入置信度和人工确认）。

3. **用例详情页执行入口**
   - 列表页已有执行入口。
   - 详情页需补齐显式“运行 / 重新运行 / 跳执行记录”操作位与状态联动。

4. **“必须执行成功”定义**
   - 技术上“成功调起执行并产出 run_id + 进入执行页”可保证。
   - 业务断言成功受环境、账号、数据、元素健康影响，需门禁与预检保证。

## 4. 核心转化机制（需求测试点 + 页面对象 -> 可执行用例）

## 4.1 转化输入

- 来自需求解析的 `test_intents`：
  - `title/priority/scene_type`
  - `precondition`
  - `steps`
  - `expected_result`
  - `involved_elements`
- 来自页面对象库的 `PageElement`：
  - `element_code`
  - `locator_type`
  - `locator_value`

## 4.2 转化规则

1. 候选用例继承 intent 的完整语义字段。
2. 生成阶段写入 `execution.steps`。
3. 同步入库前做元素绑定：
   - 优先匹配已有 `target` 对应的 element code。
   - 无 target 时基于步骤语义（输入/点击/断言 + 用户名/密码/登录等关键词）匹配页面元素。
   - 回填 `target=element:<code>` 与 `locator_type/locator_value`。
4. 入库时保留步骤的执行字段，写入 `test_case_steps`。
5. 运行时由执行引擎读取 YAML / steps 调起执行。

## 4.3 目标结果

- `test_case`：业务层用例信息完整。
- `test_case_steps`：执行层可直接消费（action + target + locator + expected）。
- `page_object_refs`：建立用例与元素的引用关系，支持追踪与治理。

## 5. 测试设计 Agent 的角色（明确结论）

结论：**有参与**，且处于中间关键环节。

1. 参与点
   - 根据 `design_input` 生成 case yaml（`TestDesignAgent`）。
   - 生成执行脚本 bundle（script-generation agent）。

2. 校验/补全能力现状
   - 已有 requirement quality gate。
   - 设计失败时有 fallback case（保证链路不断，但质量会下降）。

3. 建议强化
   - 增加“设计结果质量门禁”：
     - 无 `execution.steps` 不允许入库。
     - 步骤未绑定元素比例超阈值时拦截。
   - 增加“场景配额校验 + 二次 LLM 修复”。

## 6. 用例详情页（按企业大厂标准补齐）

## 6.1 必须补齐的字段分组

1. **业务与追踪**
   - case_id / title / priority / status
   - source（manual/ai/regression）
   - requirement_trace（需求原文、intent_ids、source_ids）
   - scene_type / test_data_type

2. **执行语义**
   - precondition（结构化）
   - steps（结构化，含 locator）
   - expected_result（每步与整体）
   - data_config（参数化）

3. **资产与质量**
   - page_object_refs（引用元素、版本、健康度）
   - script_path / script_code 摘要
   - yaml_path / yaml_version
   - latest_execution（status、duration、report、artifacts）

4. **治理信息**
   - quality_gate 决策
   - risk_summary
   - 审核记录（review/audit）

## 6.2 详情页交互（必须）

- 主按钮：`立即执行`
- 次按钮：`重新执行`、`查看执行页`
- 状态条：`queued/running/passed/failed`
- 失败时：展示 `latest_failure + 关键日志 + 跳转报告`

---

## 7. 执行闭环（列表页 + 详情页）

## 7.1 列表页
- 已支持单条执行/批量执行（跳转执行页）。
- 需补齐：
  - 执行前预检（YAML 存在、steps 非空、关键 locator 有效）。
  - 失败原因提示（不是仅弹窗）。

## 7.2 详情页
- 需新增：
  - `执行` 按钮（调用 `/api/workbench/run`）
  - 成功后自动跳转 `/execution/runs?case_ids=<case_id>`
  - run_id 与执行状态轮询

## 7.3 “必须成功调起执行页面”验收定义

满足以下即判定“执行入口成功”：
1. 返回 `run_id` 且 run 状态进入 `queued/running`。
2. 前端跳转到 `/execution/runs` 且可看到该 `run_id/case_id`。
3. 运行日志流接口可订阅（SSE 正常返回）。
