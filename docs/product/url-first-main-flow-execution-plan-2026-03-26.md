# URL-First 主流程打通执行计划（2026-03-26）

> 文档日期：2026-03-26  
> 适用范围：当前 `ai-test-platform` 主链路与 `returnApply` 样板页  
> 目标原则：先打通，再固化，最后增强；不做无边界优化

## 1. 这份计划解决什么问题

当前项目已经不是“有没有能力”的问题，而是“能力是否真正连成闭环”的问题。

这份计划要解决的核心是：

`URL 输入 -> 页面分析 -> 测试点生成 -> YAML 用例 -> 工作台选中 -> Runner 执行 -> 实时日志 -> 失败留痕 -> 失败分析 -> 门禁/审计回显`

只要这条链路稳定，平台就能真正进入可落地使用状态。

## 2. 当前真实状态

截至 2026-03-26，项目已经具备这些基础能力：

- URL-first workbench 已存在
- Playwright + YAML runner 已可执行
- 退货申请页 `returnApply` 已有样板用例
- 页面分析规则已模块化
- review / gate / audit 相关链路已落盘
- 文档和运行态已有较完整的事实记录

但仍有这些现实卡点：

- 工作台需要先选中用例才允许运行
- `returnApply` 页面有筛选项，但自动化动作还不够完整
- 日期控件、下拉控件、复杂筛选的自动操作能力还不稳
- 页面本身没有分页器，不能用“全量展开”作为 UI 验收标准
- 报告生成可能受 `Allure CLI` 缺失影响，但这不应阻断主执行链

今天的主流程已继续推进到一个更具体的状态：

- `returnApply` 的登录链路已补齐真实站点按钮、`macro123` 回归密码，以及容器宿主机 URL 归一化。
- `TC_RETURN_001`、`TC_RETURN_003` 已在 `web` 容器内跑通。
- `TC_RETURN_014`、`TC_RETURN_015` 已在 `web` 容器内跑通，边界输入后页面仍能保持表格结果可见。

## 3. 总体推进原则

1. 先保主链，不扩散到旁支优化。
2. 先做确定性的链路，再做 AI 增强。
3. 先让能跑的部分稳定，再补高级交互。
4. 所有新增文档都必须带当天日期。
5. 任何阶段都要明确：人工做什么，AI 做什么，平台做什么。

## 4. 主流程拆解

### 4.1 输入源层

输入源包括：

- URL
- PRD / 需求文本
- Swagger / OpenAPI
- Git Diff
- 缺陷单
- 线上日志

当前主链优先级建议：

1. URL
2. Swagger / OpenAPI
3. Git Diff
4. 需求文本
5. 缺陷单
6. 线上日志

### 4.2 分析层

页面分析当前要做的，不是“泛化理解所有页面”，而是：

- 找到可定位元素
- 找到能支撑 smoke 的核心路径
- 找到页面的筛选项、列表项、关键按钮
- 把结果收敛成测试点和页面对象草案

### 4.3 资产层

资产层要形成最小闭环：

- 测试点资产
- Page Object
- YAML 用例
- 运行记录
- 证据清单
- 审计与门禁记录

### 4.4 执行层

执行层需要做到：

- 选中用例
- 运行用例
- 实时输出日志
- 失败时留下截图、HTML、trace、分析
- 能回到工作台查看结果

### 4.5 治理层

治理层需要做到：

- 确认点可追溯
- 门禁决策可解释
- 失败归因可复核
- 审计记录可回放

## 5. 分阶段计划

### Phase 0: 冻结边界与基线确认

目标：

- 不再无止境扩功能
- 先确认当前主链可在 `returnApply` 上复现

要做的事：

- 固定一个样板页：`returnApply`
- 固定一组样板用例：`TC_RETURN_001`、`TC_RETURN_003`、`TC_RETURN_014`、`TC_RETURN_015`
- 固定一个样板入口：工作台 `/workbench`
- 固定一个样板输出：实时日志 + 结果状态 + 失败分析

验收标准：

- 运行时不会卡在“请先选择用例”
- 执行时能看到持续日志
- 结果能回到工作台

负责人：

- 平台：自动执行
- 人工：挑选样板用例并确认结果
- AI：辅助整理失败归因和分析摘要

### Phase 1: 主执行链打通

目标：

把 `URL -> 生成 -> 选中 -> 执行 -> 回显` 这条链真正打通。

要做的事：

1. 让工作台选中用例后能稳定载入 YAML。
2. 让 `Run Test` 触发后进入真实执行，而不是停留在 UI 交互层。
3. 让 `Realtime Logs` 在执行期间持续可见。
4. 让失败证据和分析结果自动挂回当前 run。
5. 让 `returnApply` 成为样板页，后续页面照此复制。

验收标准：

- 点击运行后，状态可从 `queued` 到 `running` 再到终态
- 日志区有连续输出
- 失败时能看到明确原因
- 不再出现前置连通性报错阻断执行

负责人：

- 平台：执行、日志、结果回显
- 人工：检查关键验收点
- AI：输出失败分析、建议动作、风险摘要

### Phase 2: 用例管理层标准化

目标：

把当前“能跑的用例资产”升级成“能被平台稳定消费的用例模型”。

要做的事：

- 增加 `test_type`
- 增加 `pytest_path`
- 增加 `markers`
- 把 API / UI / 未来 Mobile 用例分层
- 把用例目录规范写清楚
- 把工作台用例列表与实际资产状态同步起来

验收标准：

- 平台能清楚区分用例类型
- 运行器能按类型分发
- 工作台不再只是一堆 YAML 文件的列表

负责人：

- 平台：数据模型、API、目录规范
- 人工：定义分类原则
- AI：辅助归类和生成初稿

### Phase 3: 页面分析到资产生成收口

目标：

把“页面分析规则”变成“可消费的资产输出”。

要做的事：

- 让页面分析输出结构化测试点
- 让测试点生成 YAML 用例
- 让 Page Object 和页面语义对齐
- 让 `returnApply` 这种页面的核心筛选能被识别

验收标准：

- 输入 URL 后，平台能产出可落盘的测试点
- 测试点能变成可运行 YAML
- 生成结果不是只给分析说明，而是能直接进入执行链

负责人：

- AI：页面分析、测试点生成、初稿输出
- 平台：结构化落盘与执行入口
- 人工：确认关键测试点是否正确

### Phase 4: 结果回传与治理固化

目标：

让每次执行都能形成可追溯结果，而不是只跑一遍就结束。

要做的事：

- 把执行记录回写工作台
- 把失败分析与证据回显到 run 页面
- 把 review / gate / audit 结果绑定到 run
- 把人工确认点和 AI 建议点区分开

验收标准：

- 任意一次 run 都能追溯到用例、证据、分析、门禁决策
- 审计链路能复查
- 失败可以复跑，也可以人工介入

负责人：

- 平台：结果存储、回显、审计
- AI：失败归因、门禁建议
- 人工：确认和放行

### Phase 5: 扩展能力

目标：

在主链稳定之后，再补高级能力。

要做的事：

- 更多输入源接入
- 批量失败聚类
- 风险排序
- 统一调度中心
- API / Mobile Runner 对齐
- 健康度分析

验收标准：

- 平台可复用到更多页面和更多项目
- 不再依赖单页手工操作才能跑通

## 6. 当前最优先处理什么

按现在的状态，优先级建议是：

1. 先固化 `returnApply` 样板链路
2. 再把工作台选中用例与运行日志打通
3. 再补测试用例管理层字段
4. 再补页面分析到 YAML 的标准化输出
5. 最后才扩展更复杂的筛选、门禁和批量治理

## 7. 人工和 AI 的分工

### 人工负责

- 确认业务目标
- 选择样板用例
- 判断输出是否符合业务预期
- 对低置信度结果做最终确认

### AI 负责

- 页面分析
- 测试点初稿
- YAML 初稿
- 失败分析建议
- 风险摘要

### 平台负责

- 运行
- 结果保存
- 日志输出
- 证据归档
- 审计回显

## 9. 本计划的完成定义

这份计划不是在描述“做很多事”，而是在描述“做到哪一步算真的完成”。

主流程完成的最低标准是：

- 一个 URL 可以进入分析
- 分析结果可以变成测试点
- 测试点可以变成 YAML
- YAML 可以在工作台选中并运行
- 运行有实时日志
- 运行结果和失败分析可回看

只要这条最小链路稳定，平台就已经具备真实落地基础。
