# DSL V3.0 演进方向与总体目标

## Summary

当前平台主干仍是 `v1` 具体执行脚本：`execution.steps` 里直接写 `action / locator_type / locator_value / expected_result`。runner 目前只能执行具体动作，如 `goto / input / click / assert_visible / assert_url`，不能直接执行 `semantic_action` 或 `semantic_assertion`。

用户提供的 `version: "2.5"` 草案方向正确，建议吸收为 DSL V2/V3 的核心蓝图，但需要增加“语义 DSL -> 编译 IR -> runner 可执行脚本”的分层，否则会把当前卡点从 locator 层转移到 semantic 层。

## 总体目标

V3.0 的目标不是“换一种 YAML 写法”，而是建立一套可追溯、可编译、可执行、可诊断的企业级测试 DSL。

核心目标：

- 业务可读：测试人员看到的是意图、场景、数据、断言，而不是 CSS 和 XPath。
- 执行稳定：元素定位从页面对象库动态解析，优先使用真实 `data-testid`。
- 生成可控：每条用例必须绑定 `source_asset_id + intent_id`，避免重复生成和覆盖混乱。
- 断言可信：`expected_result` 不再只是自然语言，而要编译成可执行 assertion。
- 报告专业：Allure 能展示业务树、步骤、数据摘要、断言、证据和失败原因。
- 批量可治理：执行前能判断哪些用例高概率成功、哪些缺数据、缺前置、缺元素或缺环境能力。

## 对用户草案的判断与调整

这份草案有很高参考价值，建议保留以下设计：

- `identity`：保留，用于 case/project/module 的稳定身份。
- `requirement.source_asset_id`：必须保留，这是解决重复生成和用例中心同步的关键。
- `scenario.preconditions`：方向正确，应替代自然语言前置条件。
- `data.category/subtype`：方向正确，可支撑有效值、非法值、边界值、数据池。
- `steps.semantic_action`：方向正确，但不能由 runner 直接执行，必须先编译。
- `assertions.semantic_assertion`：方向正确，但需要映射为具体断言规则。
- `evidence`：方向正确，应成为执行策略的一部分。

建议调整：

- `version: "2.5"` 建议改成明确版本路线：`v2.0` 做结构化 DSL，`v2.5` 做语义编译增强，`v3.0` 做智能治理与自愈。
- `repeat_click` 不建议放在全局 `scenario.user_behavior`，应优先放到具体 step，避免所有步骤都重复点击。
- `network.mode` 暂时作为声明能力，不应默认生效，因为当前 runner 未确认已有完整网络模拟能力。
- `semantic_action: input_username` 建议拆成稳定动作和业务语义，例如 `action: input` + `semantic_action: input_username`，方便编译器兜底。
- `semantic_assertion: login_success` 必须配置断言定义，例如 URL、用户名展示、菜单加载、登录态 token 等。
- `element: username_input` 必须通过页面对象库解析，DSL 中不再固化 `locator_value`。
- `data.value` 中的密码、token 等敏感数据需要标记 `sensitive: true`，报告只展示脱敏摘要。

## 推荐架构分层

第一层：Source DSL

面向测试人员和资产中心，表达业务语义。包含 `identity / requirement / scenario / data / steps / assertions / evidence`。

第二层：Execution IR

由编译器生成，表达已解析但还未执行的动作。包含标准动作、页面、元素编码、数据引用、断言类型、traceability、compiler_status。

第三层：Runner Script

兼容当前 runner 的具体脚本。包含 `goto / input / click / assert_url / assert_visible`，并带上 `locator_type / locator_value`。

第四层：Runtime Record

执行后的事实记录。包含实际使用的 locator、耗时、截图、视频、console、失败 step、失败分类、Allure 标签和报告链接。

## 分阶段路线

V1.1：补齐身份追踪

- 所有生成用例必须写入 `source_asset_id`、`intent_id`、`selected_intent_ids`。
- 用 `project + source_asset_id + intent_id` 做幂等键，先解决重复用例和用例中心不同步。

V1.2：补齐可执行断言

- 把 `expected_result` 从纯文本升级为结构化 `assertions`。
- 登录成功至少编译出 `assert_url`、用户名可见、菜单可见其中一种或多种断言。

V1.3：补齐结构化数据

- 将自然语言数据改为 typed data。
- 支持 `valid / invalid / boundary / empty / whitespace / generated / pool`。
- 禁止把“空格”“最小长度合法账号”这类描述直接当输入值。

V2.0：引入结构化 Source DSL

- 采用用户草案中的大结构：`identity / requirement / scenario / data / steps / assertions / execution / evidence`。
- 仍然编译成当前 runner 可执行格式，保持兼容。

V2.5：引入语义编译器

- `semantic_action` 映射到标准动作。
- `semantic_assertion` 映射到断言组合。
- `element` 动态绑定页面对象库，优先 `data-testid`。
- 编译前做能力检查：缺元素、缺数据、缺前置、缺 runner 能力时提前阻断。

V3.0：智能治理型 DSL

- 支持用例执行成功率预估。
- 支持批量执行前门禁。
- 支持失败自动归因：数据问题、元素问题、环境问题、断言问题、系统缺陷。
- 支持 locator 自愈建议，但不自动修改被测系统地址。
- 支持从运行证据反哺测试点、页面对象和用例质量评分。

## 验收标准

- 新 DSL 不直接修改被测系统地址，`http://localhost:5174/#/login` 作为业务事实保留。
- 同一 `source_asset_id + intent_id` 不再重复生成多个用例。
- runner 不需要直接理解 `semantic_action`，而是执行编译后的具体动作。
- 登录成功用例不只点击登录，还必须有可执行断言。
- Allure 报告能展示业务层级、步骤、断言和脱敏数据。
- 批量执行前能识别低成功率用例，并给出原因：缺数据、缺前置、缺元素、缺断言或缺环境能力。

## Assumptions

- 当前阶段先讨论架构，不改代码。
- 现有 `v1` YAML 需要继续兼容，不能一次性废弃。
- 页面对象库和真实 `data-testid` 是未来 DSL 执行稳定性的核心基础。
- V3.0 不等于更复杂的 YAML，而是“语义表达、编译治理、执行证据”三者打通。
