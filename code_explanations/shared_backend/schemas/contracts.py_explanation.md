# 📘 代码说明书
## 一句话概括
这是一个「数据清洗与标准化中心」——把各种杂乱、不规范、可能缺字段或类型错乱的网页分析原始数据（比如页面截图信息、语义理解结果、测试点计划等），统一转换成结构清晰、字段齐全、类型安全、带版本控制和质量提示（警告/置信度/是否需人工复核）的标准格式。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `schemas/contracts.py` | 提供7个核心标准化函数（`normalize_xxx_v1`），分别处理不同类型的网页分析数据契约（Contract），确保所有下游系统看到的都是干净、一致、可信赖的数据“普通话”。 |

## 🔍 核心函数/类说明
- **`normalize_page_surface_v1()`**：把“网页表面快照”原始数据（如 DOM 结构、按钮文字、表单字段、截图列表等）变成标准格式。
  - 输入：可能是 `None` 或任意结构的字典（甚至不是字典！）、页面名、请求 URL、是否开启严格校验。
  - 输出：一个标准化后的字典（含 `version`、`element_candidates`、`confidence_summary` 等固定字段） + 一串警告列表（比如“第3个候选元素没 locator_value，已丢弃”）。
  - 大白话解释：就像一位细心的图书管理员，收到一堆乱放的书（原始数据），先检查有没有缺页（字段缺失）、有没有写错分类号（类型错误），再按统一模板（封面=page，ISBN=locator_value，推荐指数=confidence）重新贴标签、排好架，并在便签纸上记下哪些书需要老师再看看（`requires_review=True`）。

- **`normalize_page_object_draft_v1()`**：把“页面对象模型”（类似自动化测试里的 Page Object）原始数据标准化，重点理清每个页面元素（按钮/输入框）的定位方式、来源（是人工写的？还是从页面自动猜的？）、靠谱程度。
  - 输入：原始数据字典、页面名、路径、是否严格模式。
  - 输出：标准化字典（含 `elements`、`element_inventory`、`coverage` 等）+ 警告列表。
  - 大白话解释：像给装修队提供一份“精装房交付清单”——原来客户只说“有个登录按钮”，现在明确写成：“主登录按钮（key='login_btn'），用 CSS 定位 `#login-form button[type=submit]`，来源是页面自动识别（不是人工写的），当前靠谱度 65%，建议人工确认”。

- **`normalize_page_semantic_model_v1()`**：把“网页语义理解”结果（比如“这是个电商商品页，主要目标是下单”）标准化，提取业务含义（页面类型、业务领域、核心动作）。
  - 输入：原始数据字典、页面名、请求 URL。
  - 输出：标准化字典（含 `page_type`、`business_domain`、`primary_actions` 等）+ 警告列表。
  - 大白话解释：像给AI助手配一副“业务眼镜”——它本来只看到一堆HTML标签，现在能告诉你：“这是一张银行转账确认页，属于‘金融’领域，用户最可能做的动作是‘确认转账’和‘取消’”。

- **`normalize_test_point_plan_v1()`**：把“测试点计划”（即该页面要测哪些功能点、怎么测、依赖什么）原始数据标准化，尤其擅长处理嵌套的依赖审查、步骤拆解、信心打分。
  - 输入：原始数据字典、是否严格模式。
  - 输出：标准化字典（含 `points` 列表、`review_summary` 统计、`coverage` 覆盖率等）+ 警告列表。
  - 大白话解释：像把一份手写的“测试大纲草稿”变成Excel表格——自动统计：共23个测试点，其中8个信心低于60%需复核，5个依赖其他页面但找不到对应元素，3个建议跳过，整体覆盖率评估为“中等”。

- **`normalize_page_analysis_bundle_v1()`**：把上面4种数据（页面表面+语义+对象+测试点）“打包”成一个完整分析报告，并计算整体健康度。
  - 输入：包含4个子模块原始数据的大字典。
  - 输出：一个大而全的标准化字典（含 `page_surface`、`page_semantic` 等子字段 + `bundle_confidence` 整体得分）+ 合并后的警告列表。
  - 大白话解释：像把体检的4份报告（血常规、B超、心电图、问诊）汇总成一张“健康总评单”，并给出综合评分（82分）和一句总结：“肝功能稍弱，建议复查；其余正常”。

- **`normalize_execution_record_v1()`**：把“测试执行记录”（谁、什么时候、跑了什么、花了多久、生成了哪些截图/日志）标准化。
  - 输入：原始执行日志字典。
  - 输出：标准化字典（含 `run_id`、`step_summary`、`evidence_index` 等）+ 警告列表。
  - 大白话解释：像把行车记录仪视频自动生成的文字摘要——“2024-05-20 14:22:03 开始执行，共跑17步，耗时42.3秒，生成截图8张、HTML快照3份、错误日志1份”。

- **`normalize_evidence_manifest_v1()`**：把“证据清单”（所有测试产生的文件：截图在哪、HTML在哪、日志在哪）标准化，方便归档和查找。
  - 输入：原始文件路径列表字典。
  - 输出：标准化字典（含 `screenshots`、`html_pages` 等分类列表 + `total_files` 总数）+ 警告列表。
  - 大白话解释：像给快递柜生成一张“取件码清单”——“A区：截图_001.png, 截图_002.png；B区：page_dom.html, network_log.json；共12件”。

- **辅助小工具函数（`_string`, `_int`, `_bool` 等）**：所有标准化函数背后默默工作的“清洁工”。
  - 输入：任意值（字符串、数字、None、甚至错误类型）。
  - 输出：安全转换后的目标类型（字符串/整数/布尔值），带默认值兜底。
  - 大白话解释：就像你家的智能插座——不管插头是圆的方的、电压高点低点，它都能稳稳输出220V标准电，不行就自动断电（返回默认值）。

## 🧩 调用关系与数据流转
```
normalize_page_analysis_bundle_v1()  ← 主入口（打包全家桶）
├─→ normalize_page_surface_v1()         ← 处理页面“长什么样”
├─→ normalize_page_semantic_model_v1()  ← 处理页面“是干什么的”
├─→ normalize_page_object_draft_v1()    ← 处理页面“怎么自动化操作”
└─→ normalize_test_point_plan_v1()      ← 处理页面“要测哪些点”

其他函数彼此独立，无直接调用：
├─ normalize_execution_record_v1()     ← 单独处理执行日志
└─ normalize_evidence_manifest_v1()    ← 单独处理文件清单
```
**数据流转关键点**：
- 每个 `normalize_xxx_v1()` 函数都接收“脏数据” → 输出“干净数据 + 警告列表”；
- `bundle` 函数会把子函数的输出原样嵌入自己结果中（如 `page_surface: {...}`），并把各子函数的警告合并到自己的 `warnings` 字段里；
- 所有函数都用 `_xxx()` 工具函数做基础清洗（比如 `_string(raw.get("page"))`），避免 `None` 或类型错误导致崩溃；
- “置信度”（confidence）像血液一样贯穿所有函数：从单个元素（0.85）→ 页面层面（0.72）→ 整个分析包（0.78），层层汇总。

## 💡 值得学习的写法
- **防御式默认值链**：`_string(raw.get("page") or page)` —— 先尝试从原始数据取，没有就用传入参数 `page`，再没有就变空字符串。三重保险，不怕数据缺失。
- **警告收集机制**：每个函数都维护一个 `warnings: list[str]`，遇到任何异常（类型不对、字段缺失、版本不符）都追加一条人话警告，而不是直接报错中断。让程序“带伤运行”，同时留下诊断线索。
- **置信度安全钳制**：`_confidence()` 函数强制把数字限制在 0.0~1.0 并保留2位小数（`round(..., 2)`），防止因计算误差出现 `1.0000000001` 这种诡异值。
- **去重合并智慧**：`_dedup_strings()` 不仅去重，还自动过滤空字符串，且顺序保持插入顺序（Python 3.7+ dict 有序），保证警告/列表显示整洁。
- **Bundle 的“信任传递”设计**：`bundle_requires_review = A or B or C or D` —— 只要任一子模块标记“需复核”，整个报告就标红，体现“木桶效应”。

## ⚠️ 需要注意的地方
- **`strict=True` 是双刃剑**：开启后，缺少 `page`、`case_id` 等关键字段会直接 `raise ValueError` 中断流程。生产环境慎用，建议只在CI/质检环节开启。
- **`_dict_copy()` 的深拷贝成本**：对超大嵌套字典（如含几百个元素的 `metadata`）频繁调用 `deepcopy()` 可能拖慢性能，大数据量场景需关注。
- **版本字符串硬编码风险**：所有 `PAGE_SURFACE_VERSION = "PageSurfaceV1"` 都是常量，但若未来新增 `V2`，必须手动同步修改所有相关判断（如 `if version not in {PAGE_SURFACE_VERSION, ...}`），易遗漏。建议考虑集中式版本注册表。
- **`_list()` 和 `_dict()` 的“假安全”陷阱**：它们对非预期类型（如字符串 `"[]"`）会返回空列表/字典，掩盖了真正的数据结构错误。调试时若发现字段“莫名消失”，优先检查原始数据是否被误传为字符串。
- **`normalize_test_point_plan_v1()` 的 `steps` 解析逻辑复杂**：支持 `steps: ["点击登录", {"action":"fill", "target":"#pwd"}]` 这种混合类型，但若原始数据是 `steps: "fill #pwd"`（字符串），会被转成 `[{"raw_text": "fill #pwd"}]`，可能不符合下游预期。文档需明确约定输入格式。
