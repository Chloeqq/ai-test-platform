# 📘 代码说明书
## 一句话概括
这是一个“文件快递站”——它不自己干活，而是把项目里所有跟数据格式、校验规则、版本定义相关的“工具包”和“标准模板”统一打包出口，让其他模块能一句 `from schemas import ...` 就快速拿到需要的东西。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `schemas/__init__.py` | 全局“数据标准总入口”：把散落在不同子模块（case_ids、contracts、models、validator）里的常量、类、函数全部集中暴露出来，像超市的导购图，告诉你“要找数据规范，来这儿拿就行”。 |

## 🔍 核心函数/类说明
- **`build_case_id()`**：作用是按固定规则拼出一个唯一的测试用例编号（比如 `"web-cust-001"`）。  
  - 输入：客户名、模块名、页码等信息（或自动推断出的部分）  
  - 输出：一个格式整齐、带前缀和序号的字符串  
  - 大白话解释：就像给每个快递包裹贴上“城市-部门-单号”格式的条形码，确保全系统一看就知道它从哪来、属于哪一类、排第几个。
- **`normalize_xxx_v1()` 系列函数（如 `normalize_test_point_plan_v1`）**：作用是把用户传来的原始数据“整理成标准模样”——补默认值、转大小写、删多余空格、统一字段名等。  
  - 输入：可能是乱糟糟的 JSON 或字典（比如 `{ "testName": "登录测试", "steps": [...] }`）  
  - 输出：规整后的标准字典（比如 `{ "test_name": "登录测试", "steps": [...], "version": "v1" }`）  
  - 大白话解释：就像收快递时，不管寄件人手写还是打印的面单，快递员都会统一用打印机重打一张清晰、带条码、字段对齐的标准单——保证后面分拣、扫描、入库都不出错。
- **`TestPointPlanV1`, `PageObjectV1` 等模型类**：作用是定义“什么样的数据才算合格的测试计划”“什么样的页面对象描述才被系统认可”。  
  - 输入：无（它们是模板，不是函数）  
  - 输出：无（但用它们创建实例时，会自动检查字段是否齐全、类型是否正确）  
  - 大白话解释：就像“结婚证申请表”的官方样表——它规定了必须填姓名、身份证号、照片尺寸等，你填错了或漏了，系统当场就提醒你：“这张表不合格，重填！”
- **`ContractValidator` 类**：作用是拿着上面那些模型类（比如 `TestPointPlanV1`），去检查一段真实数据是否符合要求。  
  - 输入：一段待验证的数据（比如用户上传的 JSON 文件内容） + 对应的模型类（比如 `TestPointPlanV1`）  
  - 输出：一个 `ValidationResult` 对象，里面写着“✅ 通过”或“❌ 第3行缺少 required_field 字段”  
  - 大白话解释：就像房产中介拿着购房合同模板，一条条核对买家填的信息：身份证号位数对不对？签字有没有漏？定金金额是不是正数？——它不改数据，只当“守门员”，拦住不合格的。

## 🧩 调用关系与数据流转
```
外部模块（如 API 路由 / 数据导入脚本）
        ↓
调用 schemas 中导出的函数或类，例如：
  → normalize_test_point_plan_v1(raw_data)         # 把脏数据“洗”成标准格式
  → TestPointPlanV1(**cleaned_data)               # 用标准格式创建实例（自动校验）
  → ContractValidator().validate(instance)        # 让守门员再严格审一次
        ↓
返回 ValidationResult（含错误提示或成功标志）
        ↓
外部模块根据结果决定：存入数据库 ✅ / 返回错误给前端 ❌
```
> 💡 关键点：这个 `__init__.py` 文件本身不参与数据处理，它只是“货架标签”——所有真正干活的函数/类都藏在 `shared_backend.case_ids`、`.contracts`、`.models`、`.validator` 这些“仓库隔间”里，它只是把门打开、挂好指示牌。

## 💡 值得学习的写法
- **`__all__` 显式声明导出列表**：像一份“官方菜单”，明确告诉别人“本店只提供这些菜品”，避免别人误用内部未公开的函数（比如 `_helper_do_something_private`），提升代码可维护性。
- **按语义分组导入**：把 case_id 相关、contract 相关、model 相关、validator 相关的导入分开，并用空行隔开，就像超市把“生鲜区”“日化区”“家电区”分开，一眼看清结构。
- **版本化命名（`v1` 后缀）**：所有 `normalize_xxx_v1` 和 `XXXV1` 类都带 `v1`，为未来升级留路——以后加 `v2` 时不会冲突，老代码照用 `v1`，新功能可放心上 `v2`。

## ⚠️ 需要注意的地方
- **别在这个文件里写逻辑**：`__init__.py` 在这里纯粹是“中转站”，如果有人手滑在这里加了业务代码（比如 `def send_email(): ...`），会导致所有导入 `schemas` 的地方都意外执行发邮件——就像在商场导览图上偷偷装了个喇叭，一有人看图就自动广播。
- **`normalize_*` 函数不等于“自动修复”**：它们只做基础整理（如字段重命名、补默认值），**不会**智能猜缺失的关键字段（比如没传 `test_name`，它不会自作主张填“未知测试”）。真正的强校验靠后面的 `ContractValidator`，漏掉这步容易埋雷。
- **`VALID_SOURCE_TYPES` 和 `ALLOWED_ACTIONS` 是常量，不是函数**：新手可能误以为要调用它们（如 `VALID_SOURCE_TYPES()`），其实直接用就行（如 `if source_type in VALID_SOURCE_TYPES:`）——它们就像墙上贴的“禁止吸烟”标牌，是静态信息，不是按钮。
