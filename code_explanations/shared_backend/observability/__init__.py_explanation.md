# 📘 代码说明书
## 一句话概括
这是一个“项目健康监测工具箱”的入口文件，把所有跟日志记录、请求追踪、敏感信息保护等运维监控相关的功能打包好，让其他代码能像打开抽屉一样，轻松取用。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `observability/__init__.py` | 就像一个“智能收纳盒的标签页”——它不自己干活，但把盒子里所有工具（函数）的名字和位置整理好，告诉别人：“这些功能你都可以直接用！” |

## 🔍 核心函数/类说明
- **`build_ai_trace_context()`**：作用是为 AI 相关操作（比如调用大模型）自动打上“身份标签”，方便后续查问题时知道“这段 AI 思考过程属于哪个用户、哪次请求”。  
  - 输入：可能包含用户 ID、请求 ID、模型名等上下文信息（具体看 `ai_trace.py` 实现）  
  - 输出：一个带标记的上下文对象（类似给快递贴上“张三-订单#123-AI推理”的电子面单）  
  - 大白话解释：就像给每个 AI 的“脑内小剧场”配上唯一编号和时间戳，以后出错了，不用翻几百页日志，直接搜编号就能定位到那一段思考过程。

- **`configure_logging()`**：作用是“一键设置好整个项目的记事本规则”，比如写在哪、写多详细、要不要加颜色、敏感词怎么打码。  
  - 输入：配置参数（如日志级别 `INFO`/`DEBUG`、输出位置 `console` 或 `file`）  
  - 输出：无（它悄悄把 Python 的记事本系统调教好了）  
  - 大白话解释：就像给团队发统一的笔记本+钢笔+使用说明书——从此所有人记日志格式一致，老板查起来不头疼。

- **`get_request_id()` / `set_request_id()`**：一对“请求身份证”搭档。`set_` 是给当前请求发个临时身份证号（比如 `req-abc123`），`get_` 是随时问：“嘿，我现在处理的是哪个请求？”  
  - 输入：`set_` 接收一个字符串 ID；`get_` 不需要输入（自动找当前线程/协程里存的那个）  
  - 输出：`get_` 返回字符串 ID  
  - 大白话解释：想象你去银行办业务，取号机给你一张小票（`set`），之后无论你去柜台、自助机、还是打电话问进度，只要亮出这张票（`get`），工作人员就知道你在办哪件事——避免张三的事混进李四的日志里。

- **`redact_sensitive_payload()`**：作用是“自动给日志里的隐私信息打马赛克”，比如密码、手机号、银行卡号不会原样记下来。  
  - 输入：一段原始数据（可能是字典、JSON 字符串、HTTP 请求体）  
  - 输出：把敏感字段替换成 `***` 后的新数据（结构不变，只“美颜”隐私）  
  - 大白话解释：就像拍照前自动开启“人脸模糊+车牌打码”模式——既保留画面构图（日志结构），又守住底线（不泄露用户秘密）。

- **`summarize_http_context()`**：作用是从一次 HTTP 请求中，快速抓取关键信息（谁来的？什么方法？访问哪个地址？耗时多久？状态码多少？），浓缩成一行简明日志。  
  - 输入：FastAPI 的 `Request` 对象或类似上下文  
  - 输出：一个短字符串或字典，例如 `"POST /api/chat 200 1.2s"`  
  - 大白话解释：相当于给每次网页访问生成一句“新闻标题”，而不是录下整场对话——运维看一眼就懂发生了啥，不用逐行读原始请求。

- **`summarize_log_value()`**：作用是防止日志被超长内容刷屏（比如用户上传了 10MB 日志当参数），它会把太长的值自动截断+加省略号，或对复杂对象做安全简化。  
  - 输入：任意 Python 值（字符串、列表、嵌套字典等）  
  - 输出：一个安全、简洁、可读的字符串（如 `"['a', 'b', ...] (len=150)"`）  
  - 大白话解释：就像朋友圈发长图时自动压缩+加“点击查看原图”提示——既不让日志文件爆炸，又保留关键线索。

- **`run_logged_subprocess()`**：作用是“安全地运行外部命令（比如调用 shell 脚本、ffmpeg 转视频），同时全程记录它的输入、输出、耗时、是否成功”。  
  - 输入：命令列表（如 `["ls", "-l"]`）、超时时间、是否记录标准输出等选项  
  - 输出：一个包含结果、返回码、耗时、日志片段的结构化字典  
  - 大白话解释：就像请外包小哥帮你跑腿办事，还给他配了个随身记录仪+计时器+打卡机——回来直接交报告：“已执行，耗时3秒，结果是xxx，没报错”。

## 🧩 调用关系与数据流转
```
用户代码（如 FastAPI 路由） 
    → 调用 configure_logging() 一次（启动时设好记事本）  
    → 每次请求进来：set_request_id() 发号 → 中间件/路由里多次调用 get_request_id() 查号  
    → 处理请求体时：redact_sensitive_payload() 给密码打码  
    → 记录请求摘要：summarize_http_context() 抓关键信息  
    → 记录某个变量：summarize_log_value() 防止日志刷屏  
    → 需要调外部程序时：run_logged_subprocess() 安全执行+全程录像  
    → AI 相关逻辑中：build_ai_trace_context() 打上 AI 追踪标签  
所有这些函数产生的日志，最终都通过 Python logging 系统统一输出（由 configure_logging() 提前安排好）
```

## 💡 值得学习的写法
- ✅ `__init__.py` 中显式定义 `__all__`：像在收纳盒上贴了张“可用工具清单”，既让 IDE 智能提示更准，也明确告诉同事“官方支持这些接口，别乱扒内部函数”。
- ✅ `get_request_id()` / `set_request_id()` 成对出现：利用 Python 的 `contextvars`（或类似机制）实现“线程/协程局部存储”，让每个请求拥有独立的 ID“小抽屉”，互不干扰——这是处理并发请求日志溯源的关键技巧。
- ✅ `redact_sensitive_payload()` 和 `summarize_log_value()` 分工明确：一个专管“隐私保护”，一个专管“体积控制”，各司其职不越界，符合“单一职责”好习惯。

## ⚠️ 需要注意的地方
- ⚠️ `configure_logging()` 必须在项目启动**最早期**调用（比如 `main.py` 最开头），否则部分日志（尤其是导入阶段的）会按默认规则输出，导致格式混乱或敏感信息漏打码。
- ⚠️ `get_request_id()` 在非请求上下文（如后台定时任务、单元测试）中可能返回 `None` 或空字符串——调用前最好加判断，避免日志里突然冒出 `None` 引起困惑。
- ⚠️ `redact_sensitive_payload()` 默认只识别常见敏感字段名（如 `"password"`、`"token"`），如果项目自定义了字段名（如 `"auth_key"`），需手动扩展规则，否则会“裸奔”。
- ⚠️ `run_logged_subprocess()` 若执行耗时命令且未设 `timeout`，可能卡住整个 API 请求——务必根据场景合理设置超时，尤其在线上环境。
