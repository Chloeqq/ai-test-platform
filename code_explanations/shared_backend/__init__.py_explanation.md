# 📘 代码说明书
## 一句话概括
这是一个测试用例（比如自动化测试脚本）的“中央工具箱”，把所有和测试用例生成、校验、解析、执行相关的通用功能都打包好，方便其他模块随时取用——就像厨房里提前切好、分装好的葱姜蒜和调味料，做菜时不用现切现磨。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `__init__.py` | 不是真正干活的代码，而是“工具箱说明书+快递员”：把分散在各个 `.py` 文件里的实用函数和类统一整理、命名、对外暴露，让别人（比如 FastAPI 后端或测试执行器）能一句 `from mytestlib import build_case_id` 就直接用上，不用记一堆文件路径。|

## 🔍 核心函数/类说明
- **`build_case_id()`**：作用——给每个测试用例自动生成一个唯一又带含义的编号（比如 `"login-001"` 或 `"checkout-us-ff-003"`）。  
  - 输入：可能是一些线索，比如页面名（`"login"`）、客户代号（`"us"`）、模块名（`"ff"`），或者上一个编号（用来递增）。  
  - 输出：一个标准化的字符串 ID，比如 `"login-us-ff-004"`。  
  - 大白话解释：就像快递单号，不是随便乱编的，而是能看出“这是登录页、美国客户、风控模块的第4条用例”，方便人看、机器查、系统排序。

- **`validate_case_payload()` / `validate_case_title()` / `validate_case_description()`**：作用——检查测试用例的“身份证信息”是否合格（标题有没有超长？描述是不是空的？请求数据格式对不对？）。  
  - 输入：用户提交的测试用例原始数据（比如 JSON 或表单内容）。  
  - 输出：如果没问题就安静通过；有问题就抛出 `CaseRuleViolation` 错误，附带具体哪条规则没满足（比如“标题不能超过50字”）。  
  - 大白话解释：像机场安检——不拦你登机，但会严格检查你的证件照是否模糊、行李是否超重、登机牌日期对不对，确保每条用例“健康上岗”。

- **`compile_execution_steps()`**：作用——把用户写的“自然语言步骤”（比如“点击【提交】按钮”“等待加载图标消失”）翻译成机器能一步步执行的指令清单。  
  - 输入：原始步骤描述 + 页面结构信息（比如按钮在哪、叫什么名字）。  
  - 输出：一个可执行的步骤列表，每步含动作类型（click/wait/assert）、目标元素代码（如 `"btn_submit"`）、参数等。  
  - 大白话解释：就像把“煮一碗泡面”的菜谱（“撕开包装→倒开水→等3分钟→搅拌”）翻译成机器人能听懂的指令（“机械臂A打开盖子→水泵B注入200ml95℃水→计时器C启动180秒→搅拌器D转速60rpm”）。

- **`load_page_object_yaml()` / `merge_page_object_with_yaml()`**：作用——读取页面的“元素地图”（YAML 文件，记录了登录页的用户名框叫 `input_username`、密码框叫 `input_password` 等），并把它和代码里的页面对象合并起来。  
  - 输入：YAML 文件路径 或 YAML 内容；一个 Python 类（代表某个页面）。  
  - 输出：一个“活”的页面对象，里面所有元素都能通过 `.username`、`.password` 这样的属性直接调用。  
  - 大白话解释：就像给扫地机器人装上你家户型图——它本来只会乱转，但有了地图（YAML），就知道“沙发底下要重点吸”“厨房瓷砖要调大吸力”，元素定位从此精准不抓瞎。

- **`resolve_element_code()` / `resolve_involved_element_codes()`**：作用——根据用户写的模糊描述（比如“点一下那个蓝色的确认按钮”），从页面地图里智能找出对应的真实元素代号（如 `"btn_confirm_primary"`）。  
  - 输入：一段文字描述 + 页面元素字典。  
  - 输出：一个或多个元素代号（字符串或列表）。  
  - 大白话解释：就像你对语音助手说“把客厅灯调暗一点”，它得先听懂“客厅灯”对应家里哪个智能开关（而不是卧室灯或台灯），这里就是干这个“指哪打哪”的活。

- **`get_alias_code_map()` / `resolve_dictionary_code()`**：作用——维护一套“别名-标准码”对照表（比如 `"US" ↔ "united_states"`，`"FF" ↔ "fraud_filter"`），让业务人员写用例时用易懂缩写，系统内部用统一编码处理。  
  - 输入：别名（如 `"US"`）或标准码（如 `"fraud_filter"`）。  
  - 输出：对应的另一方（`"united_states"` 或 `"FF"`）。  
  - 大白话解释：像公司通讯录——你搜“张经理”，它自动给你显示电话和邮箱；这里搜 `"login"`，它返回内部标准码 `"auth_login_v2"`，避免到处硬编码、改一处漏十处。

## 🧩 调用关系与数据流转
```
用户提交测试用例（JSON/表单）
        ↓
→ validate_case_title() → validate_case_description() → validate_case_payload()  
   （逐项体检，任一失败就报错中断）
        ↓（全部通过后）
→ build_case_metadata() → build_case_id()  
   （先组装元数据，再生成唯一ID）
        ↓
→ resolve_explicit_step() → resolve_element_code() → resolve_involved_element_codes()  
   （把步骤里的文字描述，翻译成真实元素代号）
        ↓
→ load_page_object_yaml() → merge_page_object_with_yaml()  
   （加载页面地图，让元素代号能真正定位到UI控件）
        ↓
→ compile_execution_steps()  
   （最终产出可执行的机器指令列表）
        ↓
→ enrich_case_metadata()（补充执行所需上下文，如环境、浏览器类型）
        ↓
→ 交给执行引擎运行（此文件不负责，但它是“最后一公里”准备者）
```

## 💡 值得学习的写法
- **按职责拆包 + `__all__` 精准导出**：把不同能力（ID生成、校验、编译、元素解析）分到不同 `.py` 文件，再用 `__init__.py` 统一“摆货架”，既清晰又可控——别人导入时只看到你想让他用的，不会被内部辅助函数干扰。
- **错误类型具名化（`CaseRuleViolation`, `ExecutionCompilerError`）**：不是笼统抛 `ValueError`，而是定义专属错误类，让上层能精准捕获并提示用户“标题违规”还是“步骤编译失败”，体验更友好。
- **函数命名即文档（`infer_client_code`, `slugify_case_part`, `normalize_run_status`）**：光看函数名就知道它大概干啥，不需要点进去猜，大幅提升阅读效率。
- **`PreviewTestPointsCompiler` 类作为“预演编译器”**：专门用于生成测试点预览（比如告诉用户“这条用例会覆盖哪些按钮和字段”），和正式执行编译分离，职责单一、互不干扰。

## ⚠️ 需要注意的地方
- **`normalize_case_id()` 和 `build_case_id()` 容易混淆**：前者是“清洗已有ID”（比如把 `"LOGIN-US-001 "` 变成 `"login-us-001"`），后者是“从零创建新ID”。用错会导致ID重复或格式混乱，建议调用前看一眼 docstring。
- **`resolve_element_code()` 依赖 YAML 数据完整性**：如果页面 YAML 里漏写了某个按钮，哪怕界面上明明有，它也找不到——必须保证“地图”和“实景”同步更新，否则编译步骤时会静默失败或报奇怪的“元素未找到”。
- **`__all__` 列表必须手动维护**：新增函数后，如果忘了加进 `__all__`，外部 `from . import *` 就导不出它（虽然不推荐用 `*`，但 IDE 自动补全和文档生成常依赖它），容易让人以为“这个功能不存在”。
- **`enrich_candidate_with_element_codes()` 名字有点绕**：“candidate” 指待加工的原始步骤对象，“enrich” 是“加料”（塞进元素代号），实际就是“给步骤填上它要操作的具体按钮/输入框是谁”。第一次见容易卡壳，建议团队内统一叫“步骤元素绑定”。
