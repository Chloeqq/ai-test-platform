# 📘 代码说明书
## 一句话概括
这是一个为数据库查询提供“翻页功能”的工具包，就像给一本厚书加了目录和书签——既支持传统「第1页、第2页…」的翻页（适合列表页），也支持「往下拉自动加载更多」的游标分页（适合信息流/朋友圈式页面）。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `pagination.py` | 提供两种分页能力（页码分页 + 游标分页）的通用工具模块，专为 FastAPI 后端搭配 SQLAlchemy 数据库设计，让接口能优雅地返回“当前数据+翻页信息”。 |

## 🔍 核心函数/类说明
- **`class PageMeta`**：分页的“小抄本”，只存翻页相关的数字信息（当前是第几页、总共多少页、有没有上一页等）。  
  - 输入：无（由外部传入 `page`, `page_size`, `total_items` 创建）  
  - 输出：一个带计算属性的对象（比如 `.has_next` 会自动算出有没有下一页）  
  - 大白话解释：就像电梯楼层数显屏旁的小字提示——“当前12楼，共36层，↑可上，↓可下”，它不装数据，只管告诉你“现在在哪、还能去哪”。

- **`class Page`**：一次分页的完整结果包，包含两样东西：① 真正要展示的数据（如20条用户信息），② 刚才说的“小抄本”（`PageMeta`）。  
  - 输入：数据列表 `items` + 分页元数据 `meta`（可选筛选/排序信息）  
  - 输出：调用 `.to_dict()` 就能直接变成 JSON，前端拿去渲染分页按钮和列表  
  - 大白话解释：相当于快递盒——里面是你要的20条商品（`items`），盒子侧面贴着一张单子（`pagination` 字段），写着“这是第3箱，共15箱，前一箱是2号，后一箱是4号”。

- **`class CursorPage`**：游标分页的专用结果包，轻量简洁，只关心“这次拉到啥”和“要不要再拉”。  
  - 输入：数据列表 `items` + 可选的 `next_cursor`（下一页的“钥匙”字符串）  
  - 输出：一个含 `items` 和 `next_cursor` 的对象，没有总页数、没有上一页——因为无限滚动不需要回头  
  - 大白话解释：像微信聊天记录往上滑——你只看到“还有更多”，系统悄悄给你一把新钥匙（`next_cursor`），下次请求时带上它，就能接着上次断的地方继续往下取，不用算总共有多少条。

- **`def paginate()`**：页码分页的“主厨”，把 SQL 查询变成带分页信息的结果。  
  - 输入：SQL 查询语句（`Select`）、数据库连接、页码、每页数量  
  - 输出：一个 `Page` 对象  
  - 大白话解释：你告诉它“我要查所有订单，按时间倒序，给我第2页，每页15条”，它就：① 先偷偷数总数（共327条）→ 算出共22页；② 再精准切出第2页的15条；③ 打包成带页码信息的快递盒返回。整个过程对调用者完全隐藏细节。

- **`def paginate_cursor()`**：游标分页的“导航仪”，实现“拉到底自动加载”的核心逻辑。  
  - 输入：SQL 查询、数据库连接、上一次返回的游标（可为空）、每页数量、按哪个字段排序  
  - 输出：一个 `CursorPage` 对象（含数据 + 下一页游标）  
  - 大白话解释：你第一次请求不带游标 → 它返回最新20条 + 一把“第20条的时间戳钥匙”；你下次带着这把钥匙来 → 它就查“比这个时间更早的记录”，再返回20条 + 新钥匙。全程不数总数、不跳页，快且稳定。

- **`def create_cursor()` / `def decode_cursor()`**：游标的“编码器 & 解码器”，把 Python 对象（如时间、ID）变成一串安全字符串（Base64），方便通过 URL 或 API 参数传递。  
  - 输入/输出：`create_cursor(item)` → 返回字符串；`decode_cursor("xxx")` → 返回字典  
  - 大白话解释：就像把“2024-05-20 14:30:00”写成密文“MTIzNDU2Nzg5MA==”，传给前端；前端下次请求时把这个密文塞回来，后端又能准确还原出原始时间，用来做条件过滤。

## 🧩 调用关系与数据流转
```
FastAPI 接口函数（如 /api/users）
         ↓ 接收 query 参数（如 page=2, page_size=10）或 cursor="MTIzNDU2..."
         ↓
┌───────────────────────┐     ┌──────────────────────────┐
│   paginate()          │     │   paginate_cursor()      │
│  （页码分页入口）     │     │ （游标分页入口）         │
└──────────┬────────────┘     └──────────┬───────────────┘
           ↓                             ↓
    total_query → count()         decode_cursor() → 获取上一页最后一条的排序值
           ↓                             ↓
    得到 total_items                构建 WHERE 条件（如 id < 12345）
           ↓                             ↓
    计算 meta（总页数等）           添加 ORDER BY + LIMIT(N+1)
           ↓                             ↓
    query.offset().limit()         执行查询 → 得到 N+1 条数据
           ↓                             ↓
    执行查询 → 得到 N 条数据        截取前 N 条，判断是否 has_next
           ↓                             ↓
    组装 Page(items, meta)       create_cursor(第N条) → next_cursor
           ↓                             ↓
    .to_dict() → JSON 响应        组装 CursorPage(items, next_cursor, has_next)
```

## 💡 值得学习的写法
- **`PageMeta` 用 `@property` 自动计算**：不用每次手动写 `if page > 1: return page-1`，而是定义 `prev_page` 属性，访问时自动算——干净又不易错。
- **游标分页多取 1 条再截断**：`limit + 1` 是经典技巧——只靠这一条就能判断“是否还有下一页”，避免额外查总数，性能翻倍。
- **`create_cursor()` 序列化时间字段智能调用 `.isoformat()`**：自动适配 `datetime` 对象和其他类型，不用开发者自己判断类型再处理。
- **`cast(Any, ...)` 强制类型转换绕过 mypy 报错**：在保证逻辑正确的前提下，优雅处理 SQLAlchemy 动态反射的类型问题，既保类型检查又不卡开发。
- **`paginate()` 和 `paginate_cursor()` 完全解耦**：同一份查询语句（`Select`）可自由切换两种分页模式，业务层无需改 SQL，只需换函数调用——高内聚低耦合的典范。

## ⚠️ 需要注意的地方
- **`paginate()` 会执行两次 SQL（count + data）**：对超大表可能变慢，如果业务允许“不显示总页数”，建议改用游标分页，或加缓存。
- **游标分页依赖严格排序字段**：必须确保 `sort_field`（如 `id`）在全表唯一且有索引，否则可能出现漏数据或重复数据（比如两个用户同秒注册，按时间排序就可能乱序）。
- **`cursor` 解码失败时返回默认值但不报错**：`decode_cursor()` 里用了 `try/except` 返回兜底字典，虽防崩但掩盖了非法游标问题——建议日志记录异常，便于排查前端传错参数。
- **`max_page_size` 默认 100 但未在 `paginate_cursor()` 中限制**：`paginate_cursor()` 的 `limit` 上限是硬编码 `100`，而 `paginate()` 可配，二者行为不一致，容易遗漏防护，建议统一提取为常量。
- **`Page.items` 直接暴露 `list[T]`，但未做深拷贝**：如果后续代码意外修改了 `page.items`（比如 `.append()`），会影响原始数据——虽不常见，但在复杂业务链路中建议注明“请勿原地修改”。
