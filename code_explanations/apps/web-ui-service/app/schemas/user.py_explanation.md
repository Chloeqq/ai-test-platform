# 📘 代码说明书
## 一句话概括
这个文件定义了用户注册时「能填什么、不能填什么」的规则，以及用户信息「怎么存、怎么读」的数据格式，就像给用户报名表加了一套智能审查员 + 标准化打印模板。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `user.py` | 定义用户创建和读取时的数据结构与校验逻辑（不负责存数据库，只管“长什么样”和“合不合理”） |

## 🔍 核心函数/类说明
- **`UserCreate` 类**：这是用户注册时提交的「报名表模板」，自带自动审查功能  
  - 输入：`username`（用户名）、`password`（密码）、`role`（角色，比如"Viewer"或"DEVELOPER"）  
  - 输出：审查通过后的干净数据（例如把 `"  DEVELOPER  "` 自动转成 `"developer"`）  
  - 大白话解释：就像学校报名系统——你填表时写“VIEWER”或“ viewer ”它都帮你转成小写的 `"viewer"`；但如果你填“admin”或“boss”，它立刻拦住你：“对不起，这个身份不能自己注册！”（因为只有 `"viewer"`/`"tester"`/`"developer"` 是允许的）
  
- **`UserRead` 类**：这是从数据库查出用户后，「标准化打包发给前端」的快递盒  
  - 输入：数据库里查到的原始数据（比如 `id=123`, `username="alice"`, `created_at=datetime(2024,...)`）  
  - 输出：一个结构清晰、字段固定、连时间类型都自动适配的 Python 对象  
  - 大白话解释：就像快递员收货后，不直接把杂乱包裹给你，而是按统一纸箱（带标签：ID、姓名、角色、是否在职、创建时间）打包好——`model_config = {"from_attributes": True}` 就是告诉系统：“别管数据库字段叫啥名，直接按我盒子上的标签去对应填！”

## 🧩 调用关系与数据流转
```
用户在网页/APP上填写注册表单 
        ↓ （HTTP 请求发送 JSON 数据，如 {"username":"bob","password":"123456","role":"TESTER"}）
FastAPI 接收请求 → 自动用 UserCreate 类「拆包+审查」  
        ↓  
审查通过 → 得到标准化对象：username="bob", password="123456", role="tester"  
        ↓  
后端把这数据存进数据库（本文件不干这事，但它是存之前的最后一道关）  
        ↓  
当需要查用户（比如显示个人主页）→ 数据库返回原始记录  
        ↓  
FastAPI 自动用 UserRead 类「装箱」→ 把数据库字段映射成 id/username/role/is_active/created_at  
        ↓  
前端收到干净、统一、可直接渲染的 JSON（如 {"id":456,"username":"bob","role":"tester","is_active":true,"created_at":"2024-05-20T10:00:00"}）
```

## 💡 值得学习的写法
- `frozenset({"viewer", "tester", "developer"})`：用不可变集合存白名单，既防止误改，又让 `in` 查找快如闪电（比列表快得多），像把常用钥匙串挂腰带上，一摸就知有没有。
- `@model_validator(mode="after")`：不是在字段填完就立刻检查，而是等所有字段都解析完、甚至做了初步转换（比如字符串转小写）之后再统一审核——就像先让报名表所有空都填完、再交由教务老师整体复核，更灵活可靠。
- `self.role.strip().lower()`：一行代码搞定「去空格 + 统一小写」，避免用户输 `"  Viewer  "` 或 `"VIEWER"` 被误拒，体验友好又省事。
- `model_config = {"from_attributes": True}`：让 Pydantic 懂得“见名知意”——不用手动写 `id=user.id, username=user.username...`，它自动把数据库模型的属性名对号入座，减少重复劳动和拼写错误。

## ⚠️ 需要注意的地方
- `UserCreate` 只校验 `role` 是否在白名单里，但**完全不检查密码强度**（比如是否含大小写字母+数字），实际项目中需额外加密码策略（如用 `re` 正则或第三方库）。
- `UserRead.created_at` 允许为 `None`，但数据库字段如果设为 `NOT NULL`，而代码里又没默认值，可能导致查数据时报错——这里埋了个“假设数据库可能没填时间”的伏笔，上线前得确认数据库 schema 是否真允许为空。
- `ALLOWED_SELF_REGISTER_ROLES` 是模块级常量，但如果未来要支持动态配置（比如管理员后台开关角色注册），硬编码在这里就会卡住，建议后期抽成配置项或数据库字段。
- `UserCreate` 的 `password` 字段明文传入并存储在对象里，**绝不能直接打日志或返回给前端**——虽然本文件没做这事，但后续任何地方打印 `user_create.password` 都会泄露密码，必须牢记：密码只用于校验/哈希，绝不裸奔。
