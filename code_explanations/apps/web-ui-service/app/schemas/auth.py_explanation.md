# 📘 代码说明书
## 一句话概括  
这个文件定义了用户登录时要提交的“报名表”（用户名和密码）以及登录成功后发给用户的“通行证”（含令牌、类型和用户信息）。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `auth.py` | 定义登录请求格式和登录成功后返回的令牌数据结构，相当于给前后端约定好“怎么填表”和“领到什么凭证”。 |

## 🔍 核心函数/类说明
- **`class LoginRequest(BaseModel)`**：作用是规定用户登录时必须提交哪些字段、字段要满足什么基本要求（比如不能是空字符串，也不能太长）。  
  - 输入：无（它本身不是函数，而是一张“表单模板”）  
  - 输出：无（但它会被 FastAPI 自动用来检查、解析和验证前端传来的登录数据）  
  - 大白话解释：就像去办图书馆借书证，这张表规定你必须写“姓名”（不能为空，也不能写1000个字），也必须写“密码”（同理），系统收到表后会先按这张表检查有没有乱填——填错就直接拦下，不往下走。  

- **`class Token(BaseModel)`**：作用是定义登录成功后，服务器返回给前端的“电子通行证”长什么样。  
  - 输入：无（也是模板）  
  - 输出：无（但实际使用时，FastAPI 会用它把 `access_token`（一串密钥）、`token_type`（固定写“bearer”，就像通行证上印着“VIP”字样）、`user`（当前登录的用户完整信息）自动打包成标准 JSON）  
  - 大白话解释：就像你通过审核后，工作人员给你一张卡片：正面印着唯一编号（`access_token`）、写着“Bearer 类型通行证”（`token_type`），背面还贴了你的照片和基本信息（`user`）。这张卡的样式就是 `Token` 类规定的——前端拿到后能一眼看懂每块内容是什么。

## 🧩 调用关系与数据流转  
（本文件纯属“画图纸”，不执行逻辑，因此没有函数调用）  
→ 前端发送登录请求（如 `{ "username": "alice", "password": "123" }`）  
→ FastAPI 框架自动用 `LoginRequest` 这张表校验请求数据（长度、是否缺失等）  
→ 校验通过后，后端业务逻辑处理登录（查数据库、核对密码…这部分不在本文件）  
→ 登录成功后，后端创建一个 `Token` 实例（填入令牌、类型、用户信息）  
→ FastAPI 自动把它转成 JSON 返回给前端  
→ 前端拿到后，把 `access_token` 存起来，以后每次请求都带上它，就像刷卡进门一样。

## 💡 值得学习的写法  
- 用 `Field(min_length=1, ...)` 直观约束字符串长度，比手写 if 判断更简洁、统一、可自动生成接口文档。  
- 把 `UserRead` 直接嵌在 `Token` 里，复用已有用户模型，避免重复定义，也保证用户信息结构始终一致（比如头像、邮箱字段不会漏掉或写错）。  
- `token_type="bearer"` 设为默认值，既符合行业惯例（OAuth2 标准），又让调用方不用每次都手动填——就像快递单上“送货上门”是默认选项，不特别说明就按这个来。

## ⚠️ 需要注意的地方  
- `LoginRequest` 只做基础校验（长度、非空），**不校验用户名是否存在、密码是否正确**——这些必须由后续的业务逻辑（比如数据库查询）完成，否则会让人误以为“表单填对就等于登录成功”。  
- `Token.user` 类型是 `UserRead`，但如果 `UserRead` 模型里包含敏感字段（如 `hashed_password`），而没做脱敏处理，就会把密码哈希意外暴露给前端！⚠️（需确认 `UserRead` 是否已剔除敏感字段）  
- 所有字段都是必填项（没加 `Optional` 或默认值），意味着前端少传 `username` 或 `password`，FastAPI 会直接返回 422 错误——这对 API 友好，但前端同学得记得传全，不然会卡在“请求失败”却找不到原因。
