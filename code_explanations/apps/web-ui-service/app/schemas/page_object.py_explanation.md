# 📘 代码说明书
## 一句话概括
这是一个定义网页自动化测试中“页面”和“页面元素”数据结构的配置文件，就像给测试工程师准备的一套标准化电子表格模板，用来统一描述：哪个项目里的哪个页面、上面有哪些按钮/输入框、它们长什么样、怎么找到、谁负责、状态如何。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `page_object.py` | 定义所有与“页面对象模型（Page Object Model）”相关的数据结构（即：页面、页面上的元素、版本、引用关系等），专供 FastAPI 接口接收/返回数据时做校验和转换用 |

## 🔍 核心函数/类说明
- **`PageObjectCreate`**：作用——描述「新建一个页面」时必须填哪些信息、哪些可以不填、每项最多/最少能写多少字  
  - 输入：一整套页面信息（如项目编码、页面名、URL、负责人等）  
  - 输出：无（它本身不是函数，而是一个“数据模具”，FastAPI 会用它自动检查用户提交的数据合不合格）  
  - 大白话解释：就像你去政务大厅办营业执照，这个类就是《企业注册申请表》的官方填写规范——哪栏必填、名字不能超120个字、状态只能选“draft”或“active”……系统拿到表就按这规矩自动审核，不用人工一条条判  
- **`PageObjectUpdate`**：作用——描述「修改一个已有页面」时允许改哪些字段（有些字段如 `project_code` 不让改，只留空或 `None` 表示“不更新”）  
  - 输入：部分字段（可选填），比如只想改页面名和描述，其他字段就留空  
  - 输出：同上，是数据模具，不执行逻辑  
  - 大白话解释：像微信修改昵称——你只填新昵称，头像、地区这些没动的字段系统就“假装看不见”，不会把你原来的头像清空；这个类就是告诉系统：“哪些字段敢动、哪些碰都不能碰”  
- **`PageElementCreate` / `PageElementUpdate`**：作用——分别是「新增一个页面元素」（如登录按钮）和「修改该元素」的数据模具  
  - 输入：元素的各种特征（定位方式、定位值、备用定位、是否关键元素、稳定性等级、负责人等）  
  - 输出：数据模具（用于校验）  
  - 大白话解释：相当于给每个按钮/输入框发一张“身份证”，上面写着：我叫“用户名输入框”、我在网页里用 `id="username"` 找到、我的备用找法是 `name="user"`、我是关键元素、目前状态健康、由张三维护……`Update` 版本则允许你只更新其中几项（比如只改“稳定性等级”从 low → high）  
- **`PageElementVersionCreate`**：作用——记录「给某个元素拍快照/存档」时需要的信息（谁操作的、为什么存）  
  - 输入：操作人、存档原因（如“修复定位失效问题”）  
  - 输出：数据模具  
  - 大白话解释：就像Git提交代码时写 commit message——不改变元素本身，但记一笔“这一刻我保存了它的样子”，方便以后回滚或对比  
- **`PageObjectRefCreate`**：作用——定义「这个页面被谁用了」，比如被哪个测试用例、哪个需求文档引用  
  - 输入：引用类型（test_case / requirement）、引用编号、来源（手动填的还是系统自动生成的）  
  - 输出：数据模具  
  - 大白话解释：像图书馆的“借阅记录卡”——这张卡片不描述书的内容，只说“《Python入门》这本书，被3号测试用例借走了”，方便查谁在用、影响范围有多大  
- **`CandidateGroupPromotePayload` / `CandidateGroupMergePayload` / `CandidateRejectPayload`**：作用——分别对应三种“候选元素”操作：把临时发现的元素“转正”为正式元素、把几个相似候选元素“合并”成一个、把不合格的候选元素“打回”  
  - 输入：操作所需的关键信息（如要提升的元素编码、合并目标、拒绝理由等）  
  - 输出：数据模具  
  - 大白话解释：像HR面试流程——`Promote` 是“发offer录用”、`Merge` 是“把两个实习生的活合并给一个正式员工干”、`Reject` 是“面试没过，写个评语退回人才库”  
- **`PageElementBatchDeletePayload` 等批量操作类**：作用——支持一次删多个元素/分组/候选元素，避免反复点100次删除按钮  
  - 输入：要删的编码列表（最多200个）  
  - 输出：数据模具  
  - 大白话解释：就像手机相册里“多选删除”——勾10张照片，点一下“删除”，而不是每张都点开再点删除  

## 🧩 调用关系与数据流转
这个文件本身**不包含任何函数或业务逻辑**，它只是提供了一堆「数据模具（Pydantic 模型）」。实际调用关系发生在其他文件中，例如：
```
FastAPI路由（如 /api/pages/） 
    ↓ 接收用户提交的JSON数据 
    ↓ 自动用 PageObjectCreate 或 PageObjectUpdate 进行校验和类型转换 
    ↓ 合格数据传给数据库操作函数（如 create_page_in_db()） 
    ↓ 数据库函数再可能调用 PageElementCreate 去创建关联的元素...
```
简单说：这些类是“守门员+翻译官”——守门员（校验）确保进来的数据格式正确、长度合规、取值合法；翻译官（转换）把JSON字符串变成 Python 字典或对象，方便后续代码直接 `.page_name` 取值，不用自己 `data.get("page_name")` 写一堆防御性代码。

## 💡 值得学习的写法
- 所有字段都用 `Field(...)` 显式声明必填/非必填，配合 `default=` 和 `default_factory=`，清晰表达设计意图（比如 `dict` 用 `default_factory=dict` 避免可变默认参数陷阱）  
- 大量使用 `min_length`/`max_length`/`ge`/`le` 等约束，让校验逻辑集中、可读、可复用，前端/后端/文档都能自动同步规则  
- `PageElementUpdate` 中所有字段都设为 `Optional`（`str | None`），并默认 `None`，精准表达“不传=不更新”，比用空字符串 `""` 更安全（避免误把空字符串当有效值覆盖原数据）  
- 用语义化命名区分场景：`Create`/`Update`/`BatchDeletePayload`/`PromotePayload`，一眼看懂用途，降低团队沟通成本  

## ⚠️ 需要注意的地方
- `PageElementCreate.element_code` 的 `min_length=2`，但 `PageElementUpdate.element_code` 却是 `min_length=3` ——这是个潜在不一致！如果用户新建时用了2位编码（如 `"e1"`），后续更新就会校验失败，需确认是否笔误  
- `PageElementCreate.aliases_json` 和 `semantic_tags_json` 默认是 `list[Any]`，但没限制内部结构，容易存入非法数据（如混入 dict 或 str）；理想情况应定义更具体的子模型（如 `list[AliasItem]`）  
- 所有 `changed_by`/`created_by` 字段默认值都是 `"admin"`，但真实系统中应由登录用户信息动态注入，这里只是兜底值，千万别当成真实责任人  
- `PageElementCreate.is_primary` 默认 `True`，但一个页面通常有多个元素，却没加互斥约束（比如“一个页面只能有一个 is_primary=True 的元素”），需靠业务层保证，否则数据可能逻辑矛盾
