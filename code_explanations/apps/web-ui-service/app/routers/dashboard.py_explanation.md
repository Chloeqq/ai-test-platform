# 📘 代码说明书
## 一句话概括
这个文件是「仪表盘」的“前台接待员”——它不自己干活，而是把用户（比如网页）发来的请求（如“给我看总览数据”），转手交给背后真正干活的“业务管家”（facade），再把结果原样传回去。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `dashboard.py` | 负责接收前端对仪表盘的两个请求（总览、治理），并委托给业务逻辑层处理，是 API 的“门面接口” |

## 🔍 核心函数/类说明
- **`@router.get("/overview") def get_dashboard_overview()`**：作用——响应用户访问 `/api/dashboard/overview` 这个网址时的请求  
  - 输入：自动从数据库连接池拿一个数据库会话 `db`（就像去餐厅前台领一张点餐号牌）  
  - 输出：一个字典（类似一张填好的信息卡片，含数字、列表等数据）  
  - 大白话解释：你打开仪表盘页面想看“总览”，浏览器就悄悄发了个请求到这个地址；这个函数不做计算、不查表，只说：“嘿，管家！快用这张号牌（db）去查一下总览数据！” 然后把管家递回来的卡片直接交给浏览器。
- **`@router.get("/governance") def get_dashboard_governance()`**：作用——响应用户访问 `/api/dashboard/governance` 的请求  
  - 输入：同样自动获取一个数据库会话 `db`  
  - 输出：另一个字典（另一张信息卡片，内容聚焦在“治理”相关指标）  
  - 大白话解释：和上面一样，只是这次喊的是“管家，查治理数据！”，相当于点了菜单上另一道菜。

## 🧩 调用关系与数据流转
```
用户浏览器 → 发送 GET 请求到 /api/dashboard/overview  
                ↓  
dashboard.py 中的 get_dashboard_overview() 函数被触发  
                ↓  
自动拿到 db（数据库连接）→ 交给 facade.dashboard_overview(db)  
                ↓  
facade（业务管家）内部执行真正的查询/计算 → 返回 dict 结果  
                ↓  
get_dashboard_overview() 把结果原样返回给浏览器  
                ↗  
同理，/governance 走完全一样的流程，只是调用 facade.dashboard_governance(db)
```

## 💡 值得学习的写法
- **用 `build_workbench_facade()` 提前创建 facade 实例**：就像提前雇好一位全职管家（而不是每次来客人都临时招一个），避免重复初始化，提升响应速度，也方便统一管理业务逻辑。
- **路由装饰器 + 类型提示 + `Depends(get_db)` 三连**：FastAPI 自动完成“找数据库连接→传给函数→函数用完自动关连接”的整套流程，开发者只需专注“我要什么数据”，不用操心连接怎么开、怎么关——像点外卖，你只说“我要宫保鸡丁”，平台负责接单、做饭、配送。

## ⚠️ 需要注意的地方
- **facade 是模块级变量，但未加线程/请求隔离保护**：如果 `build_workbench_facade()` 创建的 facade 内部保存了数据库连接或状态（比如缓存了某个用户的权限），在高并发下可能被多个请求互相干扰（就像共用一支笔，A 写一半，B 拿过去乱涂）。✅ 正确做法是：facade 应设计为“无状态”（只做计算，不存数据），或让每个请求都新建 facade 实例（用 Depends 注入）。
- **返回类型写的是 `dict[str, Any]`，但没说明具体字段**：前端同学看到这个返回值，只能靠猜或翻文档才知道里面有没有 `total_users`、`active_alerts` 这些字段。⚠️ 后续建议用 Pydantic 模型定义明确结构（比如 `DashboardOverviewResponse`），既让代码自文档化，又能让 FastAPI 自动生成 API 文档和校验。
