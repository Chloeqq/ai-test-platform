# 📘 代码说明书
## 一句话概括
这是一个用 FastAPI 写的「网页元素管理后台接口」，专门负责对网页中的“页面”（比如首页、商品页）和“页面里的功能模块”（比如搜索框、购物车图标）进行增删查改、审核合并、版本管理和关联分析——就像一个「网页积木工厂」的总控台。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `page_objects.py` | 定义所有和「页面对象」相关的 HTTP 接口（API），是用户（前端或测试工具）和后台数据库之间的“接待窗口”，只管收请求、转给服务层、再把结果打包返回，自己不干活。 |

## 🔍 核心函数/类说明
- **`list_page_objects()`**：作用——查出所有页面（比如“登录页”“订单页”）的列表  
  - 输入：可选筛选条件（项目代号如 `"mall"`、客户端类型如 `"web"`、状态如 `"active"`）  
  - 输出：`{"items": [...]}`，里面是页面信息的数组  
  - 大白话解释：就像在超市货架前拿个清单本，写上“只看零食区+保质期未过”的标签，然后让店员帮你把符合条件的商品全列出来。

- **`create_page_object()`**：作用——新建一个页面（比如新增“会员中心页”）  
  - 输入：`PageObjectCreate` 类型的数据（包含页面名、描述、所属项目等）  
  - 输出：`{"item": 新建的页面数据}`  
  - 大白话解释：就像在装修APP里点“+新建房间”，填好名字、户型、风格，点确定后系统给你生成一个带门牌号（`page_code`）的新房间。

- **`get_page_object()`**：作用——根据页面唯一编码（如 `"home"`）精准找到某一页  
  - 输入：`page_code`（必填）、项目代号和客户端类型（默认 `"mall"` 和 `"web"`）  
  - 输出：`{"item": 页面详情}`  
  - 大白话解释：就像用身份证号查一个人的档案——输 `"home"`，就调出首页的完整资料（谁建的、什么时候建的、用了哪些模块）。

- **`list_candidate_groups()` / `list_candidate_elements()`**：作用——查看待审核的“候选分组”和“候选模块”（AI 或爬虫自动发现的、还没人工确认是否要保留的网页元素）  
  - 输入：页面编码 + 可选筛选（比如“只看质量评级为 A 的”“只看今天会话里的”）  
  - 输出：`{"items": [...]}`，是候选组/候选模块列表  
  - 大白话解释：就像淘宝后台的“疑似新宝贝推荐池”——系统自动抓了100个可能的新按钮/新弹窗，但得人来挑哪些真要上线，哪些是误抓的。

- **`promote_candidate_group()` / `merge_candidate_group()` / `reject_candidate_group()`**：作用——对候选分组做三种决策：“升为正式”“合并到别的组”“直接丢弃”  
  - 输入：页面编码 + 分组唯一键（`group_key`）+ 决策所需补充信息（比如合并目标组、拒绝原因）  
  - 输出：`{"item": 操作后的结果}`  
  - 大白话解释：就像审稿编辑处理投稿——点“录用”（promote）、“建议并入第3期专题”（merge）、“主题不符，退稿”（reject）。

- **`batch_delete_*()` 系列函数（如 `batch_delete_candidate_groups`）**：作用——一次删多个候选项或页面元素（不是单个删，是“批量勾选删除”）  
  - 输入：页面编码 + 一个包含多个 ID 的列表（比如 `["grp_001", "grp_002"]`）  
  - 输出：`{"item": 删除统计结果}`  
  - 大白话解释：就像微信清理聊天记录——长按多选5个群，点“删除”，而不是一个个点进去删。

- **`list_page_element_versions()` / `create_page_element_version()`**：作用——管理某个模块（如“搜索框”）的历史版本（方便回滚或对比）  
  - 输入：页面+模块编码 + 版本内容（如新CSS、新文案）  
  - 输出：版本列表 或 新建的版本数据  
  - 大白话解释：就像 Photoshop 的历史记录面板——每次改完搜索框样式，都存一版快照，哪天觉得改坏了，一键恢复到上周二那版。

## 🧩 调用关系与数据流转
```
前端（浏览器/App） 
    ↓ 发送 HTTP 请求（如 GET /api/page-objects/home）
    ↓（带参数：page_code="home", project_code="mall"…）
router（page_objects.py） 
    ↓ 提取参数 + 获取数据库连接（db）
    ↓ 转发给 service 层（page_object_service.xxx()）
    ↓（纯转发，不加工数据）
page_object_service（业务逻辑层） 
    ↓ 操作数据库（查/增/删/改） + 业务规则判断（如“合并前检查是否同类型”）
    ↓ 返回原始数据（Python dict/list）
router（page_objects.py） 
    ↓ 统一封装成 {"item": ...} 或 {"items": [...]} 格式
    ↓ 返回给前端（JSON 响应）
```
✅ 所有接口都遵循同一模式：**收请求 → 拿参数 → 连数据库 → 调 service → 包结果 → 返回**，像一条标准化流水线。

## 💡 值得学习的写法
- **统一响应格式**：每个接口都返回 `{"item": ...}` 或 `{"items": [...]}`，前端不用为每个接口写不同解析逻辑，省心又防错。
- **默认值友好**：所有 `Query(default="xxx")` 都设了合理默认值（如 `project_code="mall"`），前端调用时可以省略常见参数，调试和日常使用更轻松。
- **路径即资源层级**：URL 设计非常清晰，比如 `/page-objects/{page_code}/candidate-groups/{group_key}/promote`，一眼看出这是“对某页下的某候选组执行升格操作”，符合 RESTful 直觉。
- **批量操作命名直白**：`batch_delete_candidate_groups` 这种函数名，比 `delete_groups_bulk` 更易懂，新人扫一眼就知道干啥。

## ⚠️ 需要注意的地方
- **`cascade_elements` 参数容易被忽略**：在 `delete_page_object()` 接口中，`cascade_elements=False` 是默认值，意味着删页面时**不会自动删它下面的所有模块**——如果想连带清理，必须显式传 `?cascade_elements=true`，否则可能留下“孤儿模块”。
- **`purge_duplicates` 默认关着**：`list_page_elements(..., purge_duplicates=False)` 默认不自动去重，如果页面里有重复模块（比如两个一样的“客服按钮”），列表会显示两条——需要人工判断或主动开开关。
- **所有 `payload` 都走 Pydantic 校验，但错误提示不透出**：如果前端传了非法字段（比如 `PageElementCreate` 里多了个 `xxx: int`），FastAPI 会直接返回 422 错误并列出字段问题，但当前代码没做自定义错误包装，新手看到 JSON 报错可能懵，建议后续加一层友好的中文提示。
- **`session_id` 等查询参数未强制要求，但业务可能依赖它**：比如 `list_candidate_elements(..., session_id="abc123")` 中 `session_id` 是可选的，但如果某些算法按会话聚合候选元素，不传可能导致漏数据——文档或注释里最好强调“建议传”。
