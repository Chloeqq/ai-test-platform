# 📘 代码说明书
## 一句话概括
这是一个“本地数据管家”文件，专门负责在内存和硬盘之间安全地存取、筛选、更新各种测试相关的状态数据（比如运行记录、缺陷链接、评审决定等），既保证多线程操作不打架，又自动清理过期的临时任务信息。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `store.py` | 提供统一的「数据存取接口」：把分散在硬盘上的 JSON 文件（如历史记录、缺陷列表）和内存中的临时任务（如正在跑的测试任务）都管起来，让其他代码不用操心“怎么读写文件”“怎么防并发”“过期了要不要删”这些细节。 |

## 🔍 核心函数/类说明
- **`def now_iso()`**：作用——生成当前时间的标准格式字符串（如 `"2024-05-20T14:30:45.123Z"`）。  
  - 输入：无  
  - 输出：一个表示当前时间的字符串  
  - 大白话解释：就像手机右上角显示的时间，但它是给程序看的“标准报时”，方便所有数据打上统一、可排序的时间戳。

- **`def ensure_dirs()`**：作用——确保所有需要存放数据的文件夹（比如“缺陷目录”“报告目录”）都存在，不存在就自动创建。  
  - 输入：无  
  - 输出：无（纯“铺路”动作）  
  - 大白话解释：就像你准备开个文具店，它会提前帮你把货架、仓库、收银台这些房间都建好，免得你往里放东西时发现“没地方放”。

- **`def read_json_list(path: Path) → list[dict]` 和 `write_json_list(path: Path, items)`**：作用——把一个 JSON 文件当“小本子”来用：读就是翻本子抄下所有条目；写就是清空本子，重新抄一遍新内容。  
  - 输入：文件路径 + （写时）要存的数据列表  
  - 输出：（读时）从本子里抄出来的字典列表  
  - 大白话解释：就像你有一个带编号的便利贴本子（每个便利贴是一条 `{ "case_id": "TC001", "status": "failed" }`），这个函数负责帮你“打开本子抄下来”或“擦掉重写”，而且保证格式工整（JSON）。

- **`def list_defect_items(case_id: str = "") → list[dict]`**：作用——查“缺陷链接本”，可以查全部，也可以按某个测试用例 ID（比如 `"TC001"`）精准查找它关联的所有缺陷。  
  - 输入：可选的 `case_id`（像“查谁干的？”）  
  - 输出：匹配的缺陷条目列表（按“关联时间”倒序排，最新的在最前面）  
  - 大白话解释：就像公司缺陷管理系统里的“搜索框”——不输内容就显示所有缺陷；输入一个用例号，立刻弹出它最近被关联过的所有缺陷记录，方便快速回溯。

- **`def store_run_job(run_id, job)` / `update_run_job(...)` / `get_run_job(...)`**：作用——管理“正在跑的任务”的快照（比如某次自动化测试执行中，它的进度、日志地址、当前状态等），存在内存里，带自动过期清理。  
  - 输入：任务唯一ID（如 `"run_abc123"`）+ 任务数据字典；更新时加修改内容；获取时只传ID  
  - 输出：`get_run_job` 返回该任务的最新快照（或 `None` 如果过期/不存在）  
  - 大白话解释：就像前台接待员记的一块小白板——上面写着“张三在3号机跑测试，已到第5步，最后更新是2分钟前”。这块板子只记“正在忙”的事，而且如果人走了（超5分钟没动静），接待员会自动擦掉，避免板子越写越乱。

- **`def clear_state_files()`**：作用——一键清空所有硬盘上的状态数据（历史、缺陷、评审等），变成“全新出厂设置”。  
  - 输入：无  
  - 输出：无  
  - 大白话解释：就像给你的测试工作台来一次彻底大扫除：抽屉（历史记录）、文件夹（缺陷链接）、便签墙（评审决定）……全清空，只留下干净的桌面。

## 🧩 调用关系与数据流转
```
外部代码（如API路由或前端请求）
       ↓
调用 store.py 的函数（如 list_defect_items、get_run_job）
       ↓
→ 先调用 ensure_dirs() 确保文件夹存在（像开门前先确认门没锁）
→ 再调用 read_json_list() 或 write_json_list() 读写硬盘上的 JSON 文件（和“便利贴本子”打交道）
→ 或者调用 store_run_job()/get_run_job() 操作内存中的 _RUN_JOBS 字典（和“前台小白板”打交道）
       ↓
所有对硬盘的读写，最终都委托给 state_store.xxx（本文件只是个“代劳窗口”，真正干活的是 app.services.workbench_state_store）
       ↓
对内存任务的操作（_RUN_JOBS），全程用 _RUN_LOCK 锁住，防止多人同时改同一块小白板导致写错
```

## 💡 值得学习的写法
- **“代理模式”轻量实现**：`store.py` 几乎所有函数都不自己实现读写逻辑，而是直接转发给 `state_store` 模块。这就像公司前台——客户不用知道财务、人事、IT 部门在哪，只跟前台说“我要办XX事”，前台转达即可。好处是：业务逻辑集中、替换底层存储（比如以后换数据库）只需改 `state_store`，`store.py` 完全不用动。
- **内存缓存 + 自动过期（TTL）**：`_RUN_JOBS` 用字典存任务快照，并通过 `_cache_updated_at` 时间戳 + `RUN_JOB_TTL_SECONDS` 环境变量控制过期。`get_run_job` 每次取数据前自动检查“是不是太久没更新了？”，过期就删掉并返回 `None`。这就像外卖小哥送餐，系统只记“他出发了”，但如果20分钟没更新位置，就默认“单子取消”，避免一直挂着无效状态。
- **防御性字符串处理**：所有 `run_id`、`case_id` 输入都做 `str(...).strip()`，哪怕传进来是 `None`、空格、数字，也能安全转成干净字符串。这是典型的“别让脏数据搞垮我的程序”的温柔防护。

## ⚠️ 需要注意的地方
- **文件锁未显式使用**：代码引入了 `FILE_LOCK = state_store.FILE_LOCK`，但 `store.py` 中所有读写 JSON 文件的函数（如 `read_json_list`）**并没有主动加锁**！它们依赖 `state_store` 内部是否实现了文件锁。如果 `state_store` 没锁，多个线程同时读写同一个 JSON 文件（如 `HISTORY_FILE`）可能导致数据损坏（比如两个线程同时读到旧内容，各自改完再写，后写的会覆盖前写的）。✅ 正确做法：要么确认 `state_store` 的读写函数内部已加锁，要么在 `store.py` 的 `read_json_list`/`write_json_list` 外层补上 `with FILE_LOCK:`。
- **`clear_state_files()` 是“硬清空”**：它直接把所有状态文件写成空列表 `[]`，**不会备份、不可撤销**。如果误调用（比如在生产环境），所有历史记录、缺陷链接瞬间消失。⚠️ 强烈建议：在真实项目中，此处应增加确认机制（如 `dry_run=True` 参数预览）、或写入回收站目录（而非直接清空）。
- **`list_defect_items` 的 case_id 匹配是“完全相等”**：它用 `==` 判断 `case_id`，如果实际数据里 `case_id` 存的是 `"TC001 "`（带空格）而查询传的是 `"TC001"`，就会查不到。虽然代码有 `.strip()`，但仅作用于查询参数，**文件里存的数据是否规范，它不管**。💡 建议：在 `write_defect_items` 时也统一做 `strip()`，或建立数据入库校验规则。
