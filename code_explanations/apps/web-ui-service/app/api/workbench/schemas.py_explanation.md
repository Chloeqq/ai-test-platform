# 📘 代码说明书
## 一句话概括
这个文件（`schemas.py`）是整个项目的“电子表单模板集合”，它用清晰、带默认值和校验规则的结构，定义了所有前端（比如网页按钮）或外部系统（比如自动化脚本）向后端发送数据时，**必须长什么样子、哪些字段不能少、哪些值要符合要求**——就像快递寄送前必须填的标准运单。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `schemas.py` | 定义所有 API 接口接收数据的“标准格式”（即请求体结构），确保传来的数据干净、合法、不缺关键信息 |

## 🔍 核心函数/类说明
- **`class GenerateCasePayload(BaseModel)`**：作用——描述“让 AI 自动生成测试用例”时，需要提供哪些信息。  
  - 输入：一堆字段，比如 `requirement`（需求描述）、`page`（页面名）、`prd_text`（产品文档内容）、`git_diff`（代码改动差异）等，大部分都有默认值（像填表时“城市”默认填“北京”）。  
  - 输出：无（它本身不干活，只负责“检查+整理”传进来的数据）。  
  - 大白话解释：就像你去自助餐厅点“AI厨师帮你做一道新菜”，这个类就是那张点菜单——上面列好了“主料（需求）、配料（PRD/代码改动）、口味偏好（优先级/标签）”，还贴心地帮你预填了常见选项（比如默认“P1优先级”“AI生成”标签），避免你漏填或乱填。
  
- **`class SaveCasePayload(BaseModel)`**：作用——描述“把写好的测试用例存到系统里”时的数据格式。  
  - 输入：`project`（项目名）和 `yaml_content`（用 YAML 格式写的测试用例内容，且不能为空）。  
  - 输出：无（只校验，不执行保存动作）。  
  - 大白话解释：就像你写完一份菜谱（YAML 是一种易读的文本格式），要交给厨房归档，这张“归档单”强制要求你必须交完整菜谱（`min_length=1`），不能只写个标题就交。

- **`class BatchGenerateFromTestPointAssetsPayload(BaseModel)`**：作用——描述“批量让 AI 基于多个已有测试资产（如页面元素、功能点）生成用例”的请求格式。  
  - 输入：`asset_ids`（最多 200 个测试资产 ID 列表）和 `source`（来源标识）。  
  - 输出：无。  
  - 大白话解释：就像你有一筐苹果（`asset_ids`），想请 AI 批量做成苹果派（生成用例），这筐子有大小限制（最多 200 个），不能空着来（`min_length=1`），也不能塞爆（`max_length=200`）。

- **`class AutoRunPayload(BaseModel)`**：作用——描述“自动运行一批测试”的请求格式，特别强调时间控制（比如最长等 30 分钟）。  
  - 输入：`page_urls`（最多 20 个待测网页地址）、`wait_seconds`（等待结果最长时间，默认 4 分钟，最少 30 秒、最多 30 分钟）。  
  - 输出：无。  
  - 大白话解释：就像你按下“全自动咖啡机”的启动键，它会按顺序煮 20 杯咖啡（`page_urls`），但你得告诉它：“如果某杯卡住了，最多等 30 分钟（`le=1800`），别一直傻等”，这个类就是那个带倒计时器的启动面板。

- **其余类（如 `RunCasePayload`, `DefectPayload`, `WorkbenchReviewPayload` 等）**：都是同一种角色——为不同操作（运行单个用例、提缺陷、人工评审、执行门禁决策等）定制的“标准化请求表单”，每张表单都自带字段说明、默认值、必填/长度/范围校验，确保后端收到的数据“规整、可信、可直接处理”。

## 🧩 调用关系与数据流转
这个文件本身**不调用其他代码，也不被其他代码直接调用执行逻辑**；它的角色是“被引用的模板”。实际调用流程如下（文字流程图）：

```
前端用户点击【生成用例】按钮 
        ↓
浏览器把填写好的表单数据（如 requirement="登录要支持微信扫码"）打包成 JSON 
        ↓
FastAPI 后端收到请求 → 自动用 GenerateCasePayload 类“套一下”这个 JSON 
        ↓
Pydantic 检查：字段有没有？类型对不对？长度够不够？（例如 requirement 字符串不能是空字符串） 
        ↓
✅ 校验通过 → 数据变成干净、带类型提示的 Python 对象，传给真正的业务函数（比如 generate_case()）处理  
❌ 校验失败 → FastAPI 直接返回友好错误（如“requirement 字段不能为空”），连业务函数都不进
```

→ 所有 `class XXXPayload` 都走完全相同的流程：**被 FastAPI 的路由函数声明为参数类型 → 自动触发校验与转换 → 成为后续业务逻辑的可靠输入**。

## 💡 值得学习的写法
- ✅ **默认值 + `default_factory` 巧妙分工**：`tags: list[str] = Field(default_factory=lambda: ["ai-generated"])` 表示“每次新建对象时，都新建一个独立的列表”，避免多个实例共用同一个列表导致意外修改（就像每人发一张崭新的便签纸，而不是共用一本笔记本）。
- ✅ **字段校验嵌入定义中**：`case_id: str = Field(min_length=1)` 和 `wait_seconds: int = Field(ge=30, le=1800)` 把业务规则（“ID不能空”“等待时间30秒到30分钟”）直接写在字段上，一目了然，且由框架自动执行，不用在业务代码里重复写 if 判断。
- ✅ **联合类型清晰表达可选性**：`openapi_spec: dict[str, Any] | None = None` 明确表示“可以是字典，也可以是空”，比用 `Optional[dict]` 更现代、更直白（Python 3.10+ 推荐写法）。
- ✅ **语义化命名统一风格**：所有类名都以 `Payload` 结尾（如 `RunCasePayload`），一眼就知道这是“请求载荷”，不是实体模型或响应结果，团队协作时降低理解成本。

## ⚠️ 需要注意的地方
- ⚠️ **`Field(default="")` 和 `Field(default_factory=list)` 看似一样，实则关键不同**：`default=""` 是直接赋值（安全），但 `default=[]` 是危险写法（会共享同一个列表对象！），这里全部正确使用了 `default_factory`，但如果未来有人复制粘贴改错，极易引发隐蔽 bug（比如往一个实例的 tags 里加东西，另一个实例也跟着变）。
- ⚠️ **`input_sources: list[dict[str, Any]]` 这类嵌套结构没有深层校验**：它只保证外层是“字典列表”，但不检查每个字典里是否有 `type` 或 `content` 字段——相当于只检查“快递箱里装的是盒子”，不检查盒子里的东西是否齐全。后续业务代码需自行处理内部结构，容易漏校验。
- ⚠️ **大量重复的 `project: str = Field(default="mall")`**：虽然当前项目默认是 `"mall"`，但如果未来要支持多项目并行，这里硬编码默认值可能造成误用（比如忘记传 `project` 导致跑错环境）。更健壮的做法是：部分接口应将 `project` 设为必填（去掉 `default=`），或由中间件统一注入。
- ⚠️ **`Any` 类型削弱类型安全**：`list[dict[str, Any]]` 和 `dict[str, Any]` 中的 `Any` 让 IDE 和类型检查器“睁一只眼闭一只眼”，后期维护时难以发现字段拼写错误（比如把 `url` 写成 `uul`）。建议逐步替换为更具体的 Pydantic 子模型（如 `class InputSource(BaseModel): type: str; content: str`）。
