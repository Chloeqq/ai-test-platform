# 📘 代码说明书
## 一句话概括
这是一个“工具箱包装纸”——把一堆独立的、各干各事的函数（比如生成代码、解析文本、检查质量关卡等）统一装进一个叫 `OrchestratorClient` 的小盒子，让其他代码能用统一、整齐的方式调用它们。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `workbench_generation_api/orchestrator_client.py` | 定义了一个“指挥官客户端”（`OrchestratorClient`），它不自己干活，而是负责把任务分发给背后真正干活的函数，并确保大家说话用同一种“语言”（输入输出格式）。 |

## 🔍 核心函数/类说明
- **`class OrchestratorClient`**：一个“快递中转站”或“客服前台”——你不用记住每个后端师傅（函数）叫什么、住哪、爱喝什么茶，只要找这个前台，说“我要生成”“我要解析”“帮我看看质量过没过关”，它就帮你转达、收货、再把结果原样递给你。
  - 输入：5个功能各异但配合默契的函数（通过 `__init__` 传进来）
  - 输出：无直接输出；它本身是个“容器”，但提供了5个方便调用的方法（`.generate()` 等）
  - 大白话解释：就像餐厅里的服务员——厨师（`run_generate` 等函数）在后厨做菜，你只跟服务员点单（调用 `.generate(...)`），他记下单、传给后厨、端上菜（返回结果），你完全不用进厨房。这样以后换厨师（替换成新函数），只要菜式接口不变，你点单方式完全不用改。

- **`def generate(self, **kwargs) -> dict`**：对外提供的“一键生成”按钮。
  - 输入：任意关键字参数（比如 `prompt="写个登录页"`、`language="typescript"`）
  - 输出：一个字典，比如 `{"code": "...", "files": [...]}` —— 生成的结果包
  - 大白话解释：你按了“生成”键，它立刻把你的要求原封不动转交给背后的 `run_generate` 函数，拿回结果交给你，不加料、不删减、不翻译。

- **`def parse(self, **kwargs) -> dict`**：对外提供的“智能拆解”按钮。
  - 输入：任意关键字参数（比如 `raw_text="用户要……"`）
  - 输出：一个字典，比如 `{"intent": "create_form", "fields": [...]}` —— 解析出的结构化信息
  - 大白话解释：你扔给它一段乱糟糟的自然语言（比如产品需求描述），它转手交给 `run_parse` 函数去“读心”，然后把读懂的内容（字段、动作、条件等）打包成清晰字典还给你。

- **`def extract_quality_gate(self, payload) -> dict | None`**：对外提供的“找质检单”按钮。
  - 输入：任意类型的数据（通常是前面生成或解析出来的结果，比如一整段代码或需求文档）
  - 输出：一个质检相关字典（如 `{"score": 85, "issues": [...]}`），或 `None`（没找到质检信息）
  - 大白话解释：就像从快递包裹里翻出那张“出厂检验单”——它不判断好坏，只负责把藏在数据里的质量检查信息（比如测试覆盖率、安全扫描结果）精准地“抠”出来给你看。

- **`def is_quality_gate_blocked(self, payload) -> tuple[bool, dict|None]`**：对外提供的“能不能放行？”按钮。
  - 输入：同上，一段待检数据（比如刚生成的代码）
  - 输出：一个元组，比如 `(True, {"reason": "单元测试未覆盖边界情况"})` —— 第一个是“是否拦下”（True=卡住了），第二个是原因详情（或 `None`）
  - 大白话解释：它不是质检员，而是质检员的“闸机管理员”——把数据递给真正的质检逻辑（`is_quality_gate_blocked` 函数），然后回来告诉你：“闸门关了 ✅，因为……” 或 “闸门开了 ❌，放心发版”。

- **`def render_requirement_spec_markdown(self, requirement_spec) -> str`**：对外提供的“自动生成需求文档”按钮。
  - 输入：一个需求规格字典（比如 `{"title": "用户登录", "steps": [...], "security": "需加密传输"}`）
  - 输出：一段格式优美的 Markdown 字符串（可直接渲染成网页或存为 `.md` 文件）
  - 大白话解释：你给它一张“需求草稿纸”，它立马帮你排好版、加标题、加列表、加高亮，变成一份像模像样的产品文档，省得你手动敲 `#` 和 `-`。

## 🧩 调用关系与数据流转
```
外部代码（比如 FastAPI 接口）  
      ↓ 调用 .generate(...) / .parse(...) / ...  
OrchestratorClient 实例（前台服务员）  
      ↓ 把参数原样转发给对应成员函数  
      → self._run_generate(**kwargs)  
      → self._run_parse(**kwargs)  
      → self._extract_quality_gate(payload)  
      → self._is_quality_gate_blocked(payload)  
      → self._render_requirement_spec_markdown(requirement_spec)  
      ↓ 拿到返回值（dict 或 str 或 tuple）  
      ↓ 原样返回给外部代码
```
✅ 数据全程不修改、不转换、不缓存——纯“管道式”转发，就像一根透明水管，水（数据）从哪来、往哪去，流速多快，都由两端决定，中间只是通路。

## 💡 值得学习的写法
- **依赖注入 + 类型别名组合技**：用 `RunGenerate = Callable[..., dict[str, Any]]` 这种类型别名，既让代码一眼看出“这是个能生成东西的函数”，又避免重复写冗长类型签名；再配合 `__init__` 参数注入，实现了“功能可插拔”——换生成引擎？只换传进来的函数就行，Client 本体一动不动。
- **统一接口封装**：所有方法都遵循“动词命名 + 清晰职责 + 一致返回风格”，让使用者不用查文档就能猜出怎么用（`.generate()` → 生成，`.parse()` → 解析），极大降低协作和维护成本。
- **`**kwargs` 的灵活适配**：`generate` 和 `parse` 方法用 `**kwargs` 接收参数，意味着无论背后函数未来需要加多少新参数（比如 `timeout=30`, `model="gpt-4"`），Client 层都不用改——像留了一扇万能门，各种钥匙都能开。

## ⚠️ 需要注意的地方
- **空实现风险**：这个类本身不做任何业务逻辑，如果初始化时传入的函数是 `lambda: None` 或抛异常的假函数，运行时才会暴露问题——建议在 `__init__` 里加简单健康检查（比如调用一次空参数测试是否可调），否则错误会延迟到第一次 `.generate()` 才爆发。
- **类型擦除陷阱**：`**kwargs: Any` 虽然灵活，但也放弃了类型提示的好处——IDE 无法帮你检查传了哪些参数、拼写对不对。实际项目中建议搭配 Pydantic 模型或 TypedDict 做参数校验，或至少在 docstring 里写清常用参数。
- **`payload` 含义模糊**：`extract_quality_gate` 和 `is_quality_gate_blocked` 的输入都叫 `payload`，但实际可能是字符串、字典、甚至自定义对象。如果不同函数期望的 `payload` 结构不一致（比如一个要 `{"code":...}`，另一个要 `{"ast":...}`），就会出错——这需要团队约定好“payload 协议”，并在文档或类型注解中明确。
