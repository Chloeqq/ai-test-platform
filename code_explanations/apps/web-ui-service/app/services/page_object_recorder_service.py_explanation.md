# 📘 代码说明书
## 一句话概括
这是一个「网页自动化录制服务」的核心后端模块，负责启动 Playwright 录制窗口、保存用户操作脚本、分析录制出的页面元素、评估每个元素是否稳定可靠（比如按钮、输入框），并支持一键生成测试用例草稿。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `page_object_recorder_service.py` | 录制会话的全生命周期管家：从点击“开始录制”到“停止→分析→生成测试用例”，它管启动、心跳、回放、清理、元素打分、智能命名、防误删等所有事。 |

## 🔍 核心函数/类说明
- **`create_recorder_session()`**：作用——用户点“开始录制”时调用，真正拉起一个 Playwright 录制窗口（就像打开一个浏览器小窗口让用户点点点）。  
  - 输入：项目名、客户名、页面名、要访问的网址等基本信息  
  - 输出：一个带唯一ID的录制会话对象（含脚本路径、进程号、状态等）  
  - 大白话解释：它不是在“录视频”，而是在后台悄悄运行一个浏览器，把用户每一步鼠标键盘操作，自动翻译成 Python 代码（比如 `page.click("#login-btn")`），存成 `.codegen.py` 文件——就像给程序员请了个“代码速记员”。

- **`stop_recorder_session()`**：作用——用户点“停止录制”后调用，是整套流程的“大脑中枢”，干四件大事：① 关掉录制窗口；② 解析刚生成的 Python 脚本，找出所有被点过的按钮/输入框等元素；③ 给每个元素打分（比如用 `data-testid` 定位的很稳，打0.96分；用 `xpath` 定位的容易坏，只打0.52分）；④ 把靠谱的元素存进数据库，供后续生成测试用例或页面对象使用。  
  - 输入：会话ID + 是否要联网检查这些元素现在还能不能找到（可选）  
  - 输出：包含录制步骤、元素候选列表、质量评分、页面对象状态等的完整报告  
  - 大白话解释：它像一位“质检组长”+“档案管理员”：先关掉录像机，再翻看录像脚本，把里面出现过的按钮、输入框一个个列出来，挨个打分（靠不靠谱？会不会今天能点明天就找不到了？），最后把高分选手存档，为下一步做准备。

- **`create_test_case_draft_from_session()`**：作用——用户点“生成测试用例”时调用，把一次录制过程直接变成可读、可维护的测试用例草稿。  
  - 输入：会话ID + 测试用例基础信息（名字、负责人、标签等）  
  - 输出：一个标准测试用例对象（含步骤描述、自动生成的 Python 脚本、关联的页面元素等）  
  - 大白话解释：它像一位“测试文档工程师”：把刚才录制的“点登录→输账号→点提交”这种操作，翻译成人类能看懂的步骤（“1. 点击【登录按钮】；2. 在【用户名输入框】输入‘test’…”），同时生成配套的自动化脚本和关联关系，让测试同学不用写一行代码就能拿到一份可用的测试用例。

- **`_build_element_candidates()`**：作用——给每一个录制中出现的页面元素（如按钮、输入框）计算“可靠性分数”，并给出建议（直接采用 / 需人工审核 / 直接跳过）。  
  - 输入：元素定位方式（如 `id="submit"`）、它在录制中被点了多少次、联网探测结果（这个元素现在网页上还存在吗？是否可见？是否可点击？）  
  - 输出：一个带分数、风险标签（如“文字太短”、“用了XPath难维护”）、推荐动作的字典  
  - 大白话解释：它像一位“元素面试官”：对每个候选元素问三连——① 你靠什么被找到？（`id` 很稳，`xpath` 很脆）② 你被点了几次？（点得越多越重要）③ 现在真能点吗？（联网去网页上试一下）。综合打分，85分以上直接录用，72分以上建议复核，58分以下劝退。

## 🧩 调用关系与数据流转
```
用户点击"开始录制"
        ↓
create_recorder_session() 
   → 调用 _start_codegen_process() 启动 Playwright 录制窗口 → 生成 xxx.codegen.py 脚本
        ↓
用户点击"停止录制"
        ↓
stop_recorder_session()
   → 调用 _parse_codegen_steps() 解析脚本 → 得到所有操作步骤（click/fill/navigate…）
   → 调用 _parse_codegen_script() 提取所有被操作的元素 → 得到 locator 列表（id/role/text…）
   → （可选）调用 _probe_availability() 联网检查每个元素是否还存在 → 得到探测结果
   → 调用 _build_element_candidates() 给每个元素打分 → 得到候选元素列表
   → 调用 _persist_candidate_elements() 把高分元素存进数据库
        ↓
用户点击"生成测试用例"
        ↓
create_test_case_draft_from_session()
   → 调用 _load_recorded_steps() 或 _parse_codegen_steps() 拿到步骤
   → 调用 _build_case_steps_from_recorded_steps() 翻译成中文步骤描述
   → 调用 _build_case_script_from_recorded_steps() 生成 Python 脚本
   → 调用 page_object_service.create_page_object_ref() 把元素和测试用例关联起来
```

## 💡 值得学习的写法
- **“进程注册表” `_PROCESS_REGISTRY`**：用全局字典记录所有正在运行的录制进程（PID → Popen 对象），避免进程失控变成僵尸；即使服务重启，也能优雅处理旧进程（不强制报错，而是尝试探测是否还活着），非常务实。
- **“元素打分系统”**：不是简单判断“能用/不能用”，而是多维度加权（定位方式基础分 + 使用频次加分 + 探测结果扣分 + 文字长度/内容类型风险扣分），最后归一化到 0.05~0.99 区间，并映射为 A/B/C/D 等级，结果直观可解释。
- **“语义增强命名” `_source_enhanced_candidate_semantics()`**：不光靠 `id="btn-submit"` 这种技术名，还会结合业务语义库（比如配置了“登录页”的按钮统一叫 `login_btn`），甚至能猜出密码显示开关、搜索框等业务类型，让生成的代码更贴近人话。
- **“防误删保护” `_resolve_recorder_script_path()`**：所有文件操作前，都强制检查脚本路径是否在预设的安全目录（`artifacts/page-recorder/`）内，防止恶意传入 `../../../etc/passwd` 这类路径，安全意识拉满。
- **“动态文本过滤” `_looks_dynamic_text_locator()`**：自动识别并过滤掉“订单号：20240520123456”、“余额：¥1,234.56”这类随时变化的文字，避免用不稳定文本做定位，是经验之谈。

## ⚠️ 需要注意的地方
- **Playwright 环境强依赖**：`_resolve_playwright_command()` 会检查 `playwright` 模块和二进制是否存在，如果没装或没装浏览器（`playwright install chromium`），整个录制功能直接瘫痪，错误提示虽友好但需运维提前配好。
- **图形界面限制**：`_format_codegen_launch_error()` 明确指出“缺少 X Server 无法弹窗”，意味着该服务**不能部署在纯命令行服务器**（如大多数云服务器），必须在有桌面环境的本地机器运行，或额外配置 VNC/XServer，新手极易踩坑。
- **元素定位器冲突**：`_derive_recorder_element_code()` 生成唯一元素代码时，若多个元素生成相同代码（如都叫 `home-page-btn`），会自动加 `-2`、`-3` 后缀。但如果原始名称就超长或含非法字符，可能生成大量重复后缀，导致代码混乱，需关注 `_normalize_element_code()` 的截断逻辑。
- **时间敏感操作**：`_start_codegen_process()` 有硬编码的 2.5 秒等待期（`_CODEGEN_STARTUP_WAIT_SECONDS`），若网络慢或机器卡顿，可能误判为启动失败；而 `_probe_availability()` 默认 4 秒超时，对加载慢的页面可能探测不准。
- **数据库事务边界模糊**：`stop_recorder_session()` 中 `_persist_candidate_elements()` 内部有 `db.flush()`，但外层事务未显式控制，若中间某步失败（如存 candidate group 时出错），可能导致部分数据已写入、部分未写入，状态不一致，需注意异常时的回滚策略。
