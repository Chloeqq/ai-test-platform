# 📘 代码说明书
## 一句话概括
这是一个「软件质量治理仪表盘」的后台计算引擎——它把散落各处的测试失败、门禁拦截、执行证据缺失、多源变更等杂乱数据，像一位资深质量经理一样，自动汇总、打分、归因、排序，并生成人话版结论、优先级建议和点击即查的操作链接。

## 📂 文件总览
| 文件 | 作用 |
|------|------|
| `workbench_governance_service.py` | 提供一整套“治理健康度”计算服务：从单个任务风险打分 → 聚类热点分析 → 门禁趋势预测 → 经理视角摘要 → 行动项生成，全部用纯函数实现，不依赖数据库或网络，只做数据翻译与决策建模。 |

## 🔍 核心函数/类说明
- **`build_governance_overview()`**：整个文件的“总指挥”，把所有零散数据（24小时拦截统计、失败聚类列表、高风险任务清单、Flaky用例等）喂进去，吐出一份完整的治理日报（JSON格式）。
  - 输入：质量门禁摘要、任务快照、失败聚类数据、Flaky分析、14天趋势等字典/列表。
  - 输出：一个结构清晰的大字典，包含 `risk`（风险总分）、`summary`（关键指标）、`action_items`（待办事项）、`manager_summary`（给负责人的大白话总结）等 10+ 个模块。
  - 大白话解释：就像体检中心的“综合报告生成器”——你把血压、血常规、B超、心电图等原始数据交过去，它不光给你数字，还告诉你“血压偏高需关注”“肝功能轻度异常建议复查”，并标出“下一步该挂哪个科”。

- **`_build_governance_item_score_breakdown()`**：给**每一个高风险自动化任务**打精细分（满分100），判断它到底有多“危险”。
  - 输入：一个任务的原始数据（比如：“这个任务没留证据”“它改了3个页面”“它关联API合同变更”）。
  - 输出：含7个子项得分（如“等级分”“追溯分”“变更影响分”）和最终“优先带”（critical/high/medium/low）的字典。
  - 大白话解释：就像给外卖骑手算“接单风险分”——超时次数（level_score）+ 定位不准（traceability_score）+ 送医院急诊单（factor_score）+ 偏远小区（change_impact_score）……加起来决定要不要派督导员盯梢。

- **`_build_failure_cluster_analysis()`**：把成百上千次失败按“长得像”的原则自动分组（比如“都卡在登录页”“都报 selector 找不到”），再给每组打分排序，找出最该先修的“故障热点”。
  - 输入：失败聚类列表（每个聚类含出现次数、严重程度、最近一次失败ID等）+ 高风险任务列表 + 7天趋势数据。
  - 输出：按优先级排好序的Top 3聚类 + 当前最紧急聚类的详细原因（如：“和3个高风险页面重合 + 人工复核率80% + 近期阻断上升”）。
  - 大白话解释：像地铁调度员看故障热力图——不是看“哪趟车晚点”，而是发现“西二旗站早高峰连续5天闸机故障”，立刻调维修队+加派引导员。

- **`_build_action_items()`**：把冷冰冰的数据变成产品经理/测试负责人一眼能懂的待办清单。
  - 输入：关键指标（如“有2个critical任务”“昨天门禁拦了15次”“缺5个manifest”）。
  - 输出：最多5条带标题、状态（待优先处理/持续跟进）、摘要、点击直达链接的行动项。
  - 大白话解释：就像手机管家的“一键优化”——它不告诉你“内存占用92%”，而是说：“✅ 清理微信缓存（释放2.3GB）”“✅ 关闭后台音乐APP（省电）”，点一下就干。

- **`_build_manager_summary()`**：专为技术负责人写的“一页纸周报”，全用人话，拒绝术语。
  - 输入：同上核心指标，但更侧重“要不要发版？”“团队当前瓶颈在哪？”。
  - 输出：`release_readiness`（能否推进发布）、`top_theme`（本周重点主题）、`weekly_focus`（具体动作）、`highlights`（5句关键摘要）。
  - 大白话解释：就像销售总监给CEO的汇报PPT第1页：“✅ 可继续推进（因阻断率<25%）；⚠️ 重点：补齐追溯链路（缺manifest任务↑40%）；📌 具体：下周三前补完订单模块5个manifest”。

- **`build_governance_trend()`**：画出治理健康的“心电图”，看压力是变大还是变小。
  - 输入：14天内每天的门禁放行/拦截数、风险阻断数、人工复核数等。
  - 输出：每日压力分（0~100）+ 最近7天平均分 vs 上周平均分 → 判断趋势是“恶化/改善/稳定”。
  - 大白话解释：就像健身App记录心率变异性（HRV）——不是只看今天心跳多少，而是看“连续7天恢复能力是否提升”，从而判断训练强度是否合适。

## 🧩 调用关系与数据流转
```
build_governance_overview()  ← 主入口，接收所有原始数据
    ↓ 把数据切片分发
├─ _build_governance_item_score_breakdown() ← 为每个高风险任务打分（调用 _int_value/_float_value 等安全转换）
├─ _build_failure_cluster_analysis() ← 分析失败聚类（内部调用 _severity_score / _query_href 构造跳转链接）
├─ _build_flaky_analysis() ← 关联Flaky用例与风险任务（调用 _dict_value / _list_value 做类型兜底）
├─ _build_execution_strategy() ← 生成执行策略（调用 _default_gate_recommendation 决定门禁等级）
├─ _build_manager_summary() ← 生成管理者摘要（调用 _risk_level / _risk_summary 写人话）
├─ _build_action_items() ← 生成待办清单（复用上述所有指标，调用 _query_href 生成链接）
├─ _build_risk_score_breakdown() ← 计算整体风险分（复用 critical_count/block_rate_24h 等）
└─ build_governance_trend() ← 计算14天趋势（调用 _parse_timestamp 解析时间，_list_value 安全取列表）

所有辅助函数（_int_value, _float_value, _risk_level, _query_href 等）被上述函数高频调用，像“螺丝刀”“胶带”一样提供基础工具。
```

## 💡 值得学习的写法
- **防御式数据清洗无处不在**：每个 `_xxx_value()` 函数（如 `_int_value`, `_dict_value`）都自带“容错铠甲”——输入 `None`/空字符串/错误类型？统统返回安全默认值（0/{}）。避免 `KeyError` 或 `TypeError` 搞崩整份报告。
- **URL 构造智能又人性化**：`_query_href()` 不仅拼接参数，还自动处理布尔值（`True→"1"`）、列表（`["a","b"]→"a,b"`）、空值过滤，连 `Z` 时区都能自动转成 `+00:00`，生成的链接干净可读。
- **评分逻辑“可解释、可调试”**：所有打分函数（如 `_build_governance_item_score_breakdown`）都把每一分怎么来的清清楚楚拆成 `level_score`、`traceability_score`… 最终总分 = 各项相加。方便业务方质疑时快速定位：“为什么这个任务分这么高？哦，是因为它关联了API合同变更（+8分）。”
- **人话摘要层层递进**：从 `_risk_level(75)→"高"` → `_risk_summary(level="高", critical_count=2)→"存在关键治理风险任务..."` → `_build_manager_summary()` → 最终 `action_items`，像剥洋葱一样由粗到细，确保不同角色（工程师/经理/总监）各取所需。
- **“热点关联”思维巧妙**：在聚类分析和Flaky分析中，主动寻找跨维度重合（如“失败聚类的queue名”是否在“高风险任务page列表”里，“Flaky模块名”是否等于“风险任务page名”），把孤立问题连成网，直击根因。

## ⚠️ 需要注意的地方
- **时间解析隐含陷阱**：`_parse_timestamp()` 会把无时区时间（如 `"2024-01-01T12:00:00"`）强行加上 UTC 时区，但如果上游数据本意是本地时区（如北京时间），会导致时间错位8小时。务必确认所有输入时间戳已标准化为 ISO 8601 带时区格式（推荐 `"2024-01-01T12:00:00+08:00"`）。
- **分数阈值是硬编码，非配置化**：`_risk_level()` 中 `70→高`、`40→中`，`_build_governance_item_score_breakdown()` 中 `70→critical` 等阈值直接写死。业务规则变化时需全局搜索修改，建议未来抽成配置常量。
- **列表/字典判空靠 `isinstance()`，别信 `if value:`**：代码中所有对 `value` 的安全取值都用 `isinstance(value, list)` 而非 `if value`，因为 `[]` 和 `{}` 在 `if` 中为 `False`，但空列表/字典可能是有效业务状态（如“暂无关联风险任务”），直接判空会丢失语义。
- **`_default_gate_recommendation()` 是兜底逻辑，但可能被覆盖**：它只在 `task_summary` 中未提供 `gate_recommendation` 时才触发。如果上游数据漏填了推荐门禁，这里会生效；但如果填了错误值（如 `"allow"` 却实际应 `block`），此函数不会纠正——责任在数据源头。
- **`build_governance_trend()` 缓存机制有内存风险**：它用 `snapshot_cache` 缓存每个 `run_id` 的治理快照，若 `history_items` 中 `run_id` 极多（如10万+），可能导致内存暴涨。生产环境需加缓存大小限制或改用 LRU 缓存。
